## 深入理解与原有知识

## 这一讲解决什么问题

学完 embedding 之后，很多读者会自然问：

```text
既然 AI 能找到语义接近的材料，那是不是把资料放进知识库，它就能准确回答？
```

答案是：不一定。

RAG 解决的是“让模型有机会基于外部资料回答”，但它不自动保证资料正确、检索完整、理解准确、结论可发布。

这一讲把 RAG 拆开讲清楚：它是什么、为什么需要它、怎么工作、会错在哪里，以及作为使用者应该怎么检查。

## 先看一个场景

假设你在公司内部问 AI：

```text
产品 A 的企业版是否支持单点登录？如果支持，怎么开通？
```

如果模型只靠自己已有知识，它可能不知道你公司的产品 A，也可能把其他产品的经验套过来。

更可靠的做法是：

1. 先从公司产品手册、FAQ、更新日志里找相关材料。
2. 把找到的材料放进当前上下文。
3. 再让模型基于这些材料回答。

这就是 RAG 的基本思路。

## RAG 是什么

RAG 是 Retrieval-Augmented Generation 的缩写，可以理解成：

```text
检索增强生成
```

用更直接的话说：

```text
先检索相关资料，再让模型基于资料生成回答。
```

它不是一个单独的模型，也不是一个万能知识库按钮。它是一条工作链路：

```text
用户问题
  -> 检索相关资料
  -> 把资料放进上下文
  -> 生成回答
  -> 标注依据和不确定性
```

RAG 的重点在“先找依据，再回答”。这和直接让模型凭经验回答有本质区别。

## 为什么需要 RAG

生成模型本身不适合直接承担所有事实任务，尤其是这些场景：

- 公司内部资料。
- 最新政策、产品版本、价格规则。
- 项目专属背景。
- 客户合同和交付约定。
- 大量文档中的细节问答。

这些内容要么不在模型训练数据里，要么已经变化，要么只存在于你的资料库中。

RAG 的价值是把外部资料临时取出来，让模型在“看见材料”的前提下回答。

## RAG 和 embedding 的关系

embedding 常用于 RAG 的检索环节。

可以这样理解：

| 概念 | 在链路中做什么 |
|---|---|
| embedding | 把问题和文档段落变成语义坐标，帮助系统找相近材料 |
| 检索 | 从资料库里取出最相关的若干段原文 |
| 上下文 | 把这些原文交给模型当前这次回答使用 |
| 生成模型 | 基于取回的材料组织回答 |

所以，embedding 不是 RAG 的全部。RAG 的质量还取决于资料质量、文档切分、检索策略、上下文组织、生成约束和人工检查。

## 一个完整流程

假设知识库里有一份产品手册：

```text
产品 A 企业版支持单点登录。
开通条件：企业管理员提交域名验证，并在后台配置身份提供商信息。
当前只支持企业版，不支持个人版。
```

用户提问：

```text
客户问产品 A 能不能接公司自己的登录系统，应该怎么回复？
```

一个简化的 RAG 流程是：

1. 系统把问题变成 embedding。
2. 系统在知识库里找语义接近的文档段落。
3. 找到“企业版支持单点登录”的段落。
4. 把原文段落放进模型上下文。
5. 模型基于段落生成回复。
6. 输出中标注依据、适用范围和待确认信息。

比较稳的回答会像这样：

```text
根据当前产品手册，产品 A 企业版支持单点登录。
开通前需要企业管理员完成域名验证，并在后台配置身份提供商信息。

需要注意：
- 该能力当前只适用于企业版。
- 如果客户使用的是个人版，需要先确认是否可升级。
- 具体配置步骤建议以最新后台说明或实施文档为准。
```

这里最重要的不是回答看起来完整，而是它把“依据、适用范围、待确认事项”分开了。

## RAG 会错在哪里

### 1. 资料本身不可靠

如果知识库里有旧版本文档，RAG 可能把旧资料取出来。检索增强只会增强“取到的资料”，不会自动判断资料是否过期。

### 2. 检索找错材料

用户问“单点登录”，系统可能找到“普通登录流程”“账号密码设置”“二次验证说明”。这些材料看起来相关，但不能回答当前问题。

### 3. 文档切分不合理

如果文档切得太碎，可能只取到“支持单点登录”，却漏掉“仅企业版支持”。

如果文档切得太大，可能把登录、权限、计费、发票都混在一段里，模型容易抓错重点。

### 4. 生成阶段过度推断

材料只说“支持企业版单点登录”，模型却可能补出“配置一般 1 个工作日完成”“支持所有身份提供商”。这些补充如果材料没有写，就不能直接采用。

### 5. 用户问题太模糊

用户只问：

```text
客户登录系统怎么处理？
```

系统很难判断是“单点登录”“普通账号登录”“验证码登录”还是“权限异常”。问题越模糊，检索越容易偏。

## RAG 输出怎么检查

看到一个基于知识库的回答，不要只看它顺不顺。先检查四件事：

| 检查项 | 要问的问题 |
|---|---|
| 找到什么 | 它引用或依据了哪些原文材料？ |
| 是否适用 | 原文是否适用于当前产品、版本、客户类型和时间？ |
| 是否完整 | 有没有漏掉限制条件、例外情况或前置条件？ |
| 是否越界 | 有没有把材料没写的内容补成确定结论？ |

如果系统不能展示依据，使用者就要更谨慎。没有依据的知识库问答，本质上很难和普通生成回答区分。

## 好问题怎么写

比较弱的问题：

```text
产品 A 支持单点登录吗？
```

更好的问题：

```text
请基于公司知识库回答：
产品 A 是否支持企业客户使用单点登录？

要求：
1. 先列出你找到的相关原文标题或段落。
2. 再回答是否支持。
3. 必须说明适用版本、开通条件和限制。
4. 如果材料没有写，不要补充确定结论，列为待确认。
```

这段提问把检索、回答、边界和不确定性都说清楚了。

## RAG 和普通搜索有什么区别

| 能力 | 普通搜索 | RAG |
|---|---|---|
| 找资料 | 搜索结果列表 | 检索相关段落 |
| 组织回答 | 人自己读和整理 | 模型基于段落生成回答 |
| 风险 | 搜索结果需要筛选 | 检索错或生成错会被包装成完整回答 |
| 适合场景 | 查外部公开信息 | 基于指定资料库问答、内部知识助手 |

RAG 更方便，但也更容易让人放松警惕。因为它给出的不是一堆链接，而是一段顺滑回答。

## 常见误解

### 误解一：接了知识库就不会幻觉

不会。RAG 只是增加了资料依据，仍然可能检索错、漏掉限制、误解原文或过度推断。

### 误解二：知识库越大越好

不一定。知识库越大，越需要清晰的文档结构、标题、版本、权限和更新机制。混乱资料越多，检索越容易取到相似但不适用的内容。

### 误解三：RAG 可以替代内容建设

不能。RAG 依赖好的内容。内容本身没有结构、没有版本、没有边界，AI 只会把混乱更快地暴露出来。

## 判断清单

设计或使用 RAG 知识库时，先问：

- 文档是否有清晰标题和更新时间？
- 关键限制条件是否和正文放在一起？
- 同一问题是否存在新旧版本冲突？
- 系统是否能展示引用来源？
- 回答是否区分材料事实、模型推断和待确认信息？
- 高风险回答是否需要人工确认？

## 练习

拿一份你熟悉的资料，例如产品说明、项目 FAQ 或内部流程文档。

完成三步：

1. 写一个模糊问题。
2. 写一个更适合 RAG 的清晰问题。
3. 列出你希望 AI 回答时必须标注的依据、限制和待确认信息。

模板：

```text
模糊问题：

清晰问题：

必须引用的资料范围：

必须说明的限制：

如果材料不足，应该列出的待确认信息：
```

## 验收标准

完成这一讲后，你应该能做到：

- 解释 RAG 是“先检索，再生成”，不是知识库魔法。
- 说明 embedding、检索、上下文和生成模型在 RAG 中的分工。
- 判断一个 RAG 回答是否引用了真正适用的材料。
- 知道接入知识库后仍然需要核查和人工确认。
- 能把模糊问题改写成更适合知识库问答的问题。
