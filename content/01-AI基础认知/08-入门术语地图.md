## 深入理解与原有知识

## 这一讲解决什么问题

AI 术语很多：模型、prompt、token、上下文窗口、RAG、agent、workflow、eval、tool calling、embedding。

如果一开始按术语表学习，很容易越学越乱。更好的方式是用任务视角理解这些术语：它们分别解决 AI 协作中的哪个问题。

这一讲不追求完整技术解释，而是建立入门阶段够用的术语地图。它不是最终版术语教材，而是帮你知道“这个词大概解决什么问题、后面该在哪里继续学”。

如果你读完某个术语仍然不懂，可以直接让 AI 继续解释。推荐这样问：

```text
请用业务同事能听懂的方式解释 {{术语}}。
要求：
1. 先用一句话解释它解决什么问题。
2. 再用一个工作场景举例。
3. 说明它常见误解是什么。
4. 最后给我一个小练习，确认我是否理解。
```

术语不是背出来的，而是在任务里反复用明白的。

## 先看一条主线

AI 协作可以拆成五个问题：

```text
谁来生成
依据什么生成
怎么告诉它任务
怎么让它做多步事
怎么判断结果好坏
```

大部分术语都可以放进这条主线里。

## 核心术语

### 模型

模型是生成回答的核心能力。你可以把它理解成“根据上下文生成候选结果的系统”。

入门阶段只需要知道：

- 不同模型能力不同。
- 同一个模型在不同上下文下表现不同。
- 模型不是天然的事实数据库。

### Prompt

Prompt 是你给 AI 的任务输入。它不是咒语，而是任务说明。

一个好的 prompt 通常包含：

- 目标。
- 背景。
- 材料。
- 约束。
- 输出格式。
- 验收标准。

### Context

Context 是 AI 当前能看见的信息，包括你的任务、材料、对话历史和工具返回结果。

很多输出不稳定，不是 prompt 句式不够高级，而是 context 不够清楚。

### Token

Token 可以粗略理解成模型处理文字的基本单位。入门阶段不需要精确计算，只要知道：模型一次能处理的信息量有限。

这就是为什么长文档、长对话和大量材料需要整理结构。

### Embedding

Embedding 可以理解成“把文字变成一组数字坐标”，用来表示语义相近关系。更完整的讲解见：[Embedding 与语义检索](04-Embedding与语义检索.md)。

例如：

```text
注册时验证码一直收不到
短信码没发过来，卡在登录页
```

这两句话用词不完全一样，但都在说“验证码/短信码导致无法继续”。embedding 的作用，就是让系统能判断它们在意思上更接近，而不是只看有没有相同关键词。

它常用于这些场景：

- 判断两段文字是否相似。
- 从知识库里找和问题相关的材料。
- 把资料按主题聚类。

入门阶段只需要知道：embedding 帮系统找“相关内容”，但不负责写答案，也不保证找到的内容一定完整、一定正确。找到相关材料以后，通常还要由生成模型基于材料组织回答。

判断它有没有用对，重点看三件事：

- 它找到的原文是否真的回答当前问题。
- 它是否混淆了“相似但不同”的场景。
- 它有没有把材料事实和模型推断分开。

### 上下文窗口

上下文窗口是模型一次能看见的信息范围。超出范围的信息，模型不能稳定使用。更完整的讲解见：[上下文窗口与记忆](05-上下文窗口与记忆.md)。

因此重要背景要明确放进当前任务，而不是指望 AI 永远记得。

### RAG

RAG 可以粗略理解成“先从资料库取相关材料，再让模型基于材料回答”。更完整的讲解见：[RAG 与知识库问答](06-RAG与知识库问答.md)。

它解决的问题是：模型本身不一定知道最新或专属资料，所以需要把外部知识取进上下文。

入门阶段要记住：RAG 不是让 AI 永远正确，它只是让 AI 有机会基于指定材料回答，仍然需要核查。

### Tool

Tool 是 AI 可以调用的外部工具，例如搜索、计算、读取文件、操作系统、访问数据库。

工具让 AI 不只生成文字，还能获取信息或执行动作。但工具越多，越需要权限、日志和检查。

### Workflow

Workflow 是多步骤流程。它把复杂任务拆成若干稳定步骤，例如“收集材料 -> 摘要 -> 标注事实 -> 生成初稿 -> 核查 -> 修改”。更完整的讲解见：[从单次任务到 Workflow](../05-工作流与方法沉淀/02-从单次任务到Workflow.md)。

workflow 解决的是复杂任务不稳定的问题。

### Agent

Agent 可以理解成带目标、工具和循环的任务执行体。它不只是回答一句话，而是可以围绕目标多步执行。更完整的讲解见：[什么时候需要 Agent](../05-工作流与方法沉淀/03-什么时候需要Agent.md)。

但 agent 不是入门阶段的默认答案。只有任务需要多步执行、工具调用、状态跟踪和异常处理时，才值得考虑。

### Eval

Eval 是 evaluation 的缩写，可以理解成“评估、测试、打分”。

它解决的问题是：不要只凭一次输出感觉 AI 好不好，而是用固定样例和固定标准测试一个 prompt、workflow 或 AI 输出是否稳定有效。

入门阶段的 eval 可以很简单：用评分表检查事实准确、结构完整、风险标注、读者适配。更完整的讲解见：[如何设计轻量 Eval](../04-判断验证与风险/04-如何设计轻量Eval.md)。

## 术语之间的关系

| 问题 | 对应术语 | 入门理解 |
|---|---|---|
| 谁生成回答 | 模型 | 根据上下文生成候选结果 |
| 它看见什么 | context、上下文窗口、token | 当前可用信息有限 |
| 怎么下任务 | prompt | 任务说明，不是咒语 |
| 怎么找相关材料 | embedding、RAG | 用语义相近关系找到资料，再放进上下文 |
| 怎么用外部工具 | tool | 调用搜索、计算、文件、数据库等外部能力 |
| 怎么做复杂任务 | workflow、agent | 把一次回答变成多步流程 |
| 怎么判断好坏 | eval | 用标准测试结果 |

## 常见误解

### 误解一：学 AI 就要先学所有术语

不需要。先学任务、上下文和验收，再逐步理解术语。

### 误解二：用了 RAG 就不会错

RAG 只是提供材料，模型仍可能漏读、误解或过度推断。

### 误解三：agent 一定比 prompt 高级

不是。简单任务用 prompt 更快，更容易控制。复杂任务才需要 workflow 或 agent。

## 验收标准

完成这一讲后，你应该能做到：

- 用任务视角解释模型、prompt、context、embedding、RAG、workflow、agent、eval。
