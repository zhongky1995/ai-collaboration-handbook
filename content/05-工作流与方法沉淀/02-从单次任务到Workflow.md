## 步骤清单怎样升级为可恢复的 Workflow？

Workflow 的核心不是步骤清单，而是状态与转换：每个状态都有可观察产物，失败能停在可恢复位置。

### 在固定研究简报中操作

把研究流程写成 received → extracting → comparing → drafting → verifying → ready_for_review，并补来源冲突分支和人工门。

### 在「从单次任务到 Workflow」中最容易犯的错

只有动作没有状态，失败后就不知道已经产出什么、从哪里继续。

### 「工作流」应留下什么证据

- **结构检查**：每个状态有可观察产物，并含人工门与至少一个异常分支。
- **固定案例对照**：说明这次修改解决了哪一种失败，并保存进「工作流」。
- **需人工核验**：事实、业务适用性与高风险决定仍由人负责。

本页为主脊柱增加 **步骤、状态、检查点、人工门与异常分支**；满足以上证据后，回到作品继续推进 Agent Loop：只把动态分支交给循环。

## 深入理解与原有知识

## 这一讲解决什么问题

当任务只有一步时，prompt 就够了。当任务有多个环节、多个判断点和多个输出要求时，prompt 容易变得很长，也容易不稳定。

这时需要 workflow。

Workflow 不是把 prompt 写得更复杂，而是把任务拆成稳定步骤，每一步都有输入、输出和检查点。

## 一个问题：为什么复杂任务容易失败

例如你问：

```text
请帮我做一份完整竞品分析，并给出产品建议。
```

AI 可能会同时处理：

- 竞品范围。
- 对比维度。
- 资料整理。
- 功能分析。
- 用户体验判断。
- 风险。
- 建议。

这些步骤混在一起，任何一步错了，后面的结论都会被带偏。

Workflow 的作用，就是把复杂任务拆开。

## Workflow 和 Prompt Template 的区别

很多人会把 workflow 和 prompt template 混在一起。

| 概念 | 解决的问题 | 例子 |
|---|---|---|
| Prompt | 这一次让 AI 做什么 | 请改写这封邮件 |
| Prompt Template | 重复任务的输入结构怎么复用 | 每次会议纪要都填会议背景、参会人、记录 |
| Workflow | 多步骤任务怎么稳定推进 | 先整理事实，再做推断，再生成简报，再人工验收 |

Template 解决的是“同类输入怎么复用”。Workflow 解决的是“复杂任务的步骤顺序和检查点怎么固定”。

一个 workflow 里可以包含多个 prompt template。

## Workflow 的基本结构

一个工作流至少包含：

| 元素 | 说明 |
|---|---|
| 适用场景 | 什么时候用这个流程 |
| 输入材料 | 开始前需要什么 |
| 步骤 | 每一步做什么 |
| 中间产出 | 每一步输出什么 |
| 人工确认点 | 哪一步必须由人判断 |
| 验收标准 | 最终结果如何判断 |
| 失败处理 | 如果信息不足怎么办 |

如果要更稳定，还可以加两个字段：

| 元素 | 说明 |
|---|---|
| 状态记录 | 当前完成到哪一步、有哪些待确认 |
| 交接包 | 下一步继续时需要带上的上下文、依据和产出 |

这两个字段会在长任务里很有用。复杂任务最怕“做到一半忘了前面判断”，状态记录和交接包就是防止上下文丢失。

## 示例：资料研究 Workflow

```text
适用场景：
为一次内部讨论准备研究简报。

输入材料：
访谈摘录、用户反馈、流程说明、限制条件。

步骤：
1. 写任务说明卡
   输出：研究目标、读者、材料、边界。

2. 整理事实
   输出：事实表，不做建议。

3. 做初步推断
   输出：推断表，每条绑定事实编号。

4. 拆业务流程
   输出：AI 或方案可能介入的流程环节。

5. 生成简报
   输出：内部讨论简报。

6. 人工验收
   输出：修改记录和待补资料。

人工确认点：
- 研究目标是否正确。
- 推断是否超过材料。
- 哪些内容能进入会议。

验收标准：
- 事实和推断分开。
- 关键结论有依据。
- 有待补资料清单。
```

这个 workflow 的关键不是“让 AI 写一份研究简报”，而是强制顺序：

```text
先确定任务
再整理事实
再做推断
再生成表达
最后人工验收
```

如果跳过“事实表”，直接让 AI 写建议，后面的建议很可能看起来顺，但依据不清。

## 工作流不是越细越好

常见误区是把 workflow 写成几十步。这样很难用。

好的 workflow 应该固定关键步骤，把低风险细节留给 AI 灵活处理。

例如资料研究必须固定：

- 先事实，后推断。
- 推断绑定依据。
- 不确定内容单独列出。
- 最后人工验收。

但不需要固定每句话怎么写。

## Workflow 常见失败

| 失败 | 表现 | 修正方式 |
|---|---|---|
| 步骤太粗 | “调研 -> 输出报告”，中间判断全靠 AI 猜 | 拆出事实、推断、建议、验收 |
| 步骤太细 | 几十个步骤，没人愿意用 | 保留关键判断点，合并低风险动作 |
| 没有中间产出 | 做完才发现前面错了 | 每一步都产出可检查材料 |
| 没有人工确认点 | 错误一路传到最终稿 | 在事实、推断、发布前设置停顿 |
| 没有失败处理 | 材料不足时 AI 继续编 | 明确“不足时列待补资料” |

好的 workflow 不是让任务变复杂，而是让错误更早暴露。

## 人工确认点很关键

Workflow 不是让 AI 一路自动跑到底，而是明确哪些地方必须停下来让人判断。

常见确认点：

- 目标是否正确。
- 材料是否足够。
- 结论是否过度。
- 输出是否适合读者。
- 是否可以对外发布。

没有人工确认点的 workflow，很容易把错误规模化。

## Workflow 什么时候需要 Harness

当步骤固定、人工确认点清楚时，Workflow 本身已经足够。只有出现下面变化，才需要进一步设计 Agent/Harness：

- 下一步必须根据工具结果动态选择。
- 任务会跨多轮、跨会话或跨执行者继续。
- AI 能改变文件、系统或外部沟通状态。
- 需要管理权限、重试、停止、日志和回归测试。

Harness 不是另一条更长的 Workflow，而是负责“让动态执行仍然可控”的运行外壳。先把本页 Workflow 模板写稳定，再读 [从 Prompt 到 Harness 工程](../09-Agent与Harness工程/01-从Prompt到Harness工程.md)。

## 练习

选择一个你经常做的任务，例如：

- 周报。
- 会议纪要。
- 用户反馈分析。
- 竞品观察。
- PPT 大纲。

写一个 workflow：

```text
任务名称：
适用场景：
输入材料：
步骤 1：
步骤 1 输出：
步骤 2：
步骤 2 输出：
人工确认点：
最终输出：
验收标准：
失败处理：
```

## 验收标准

完成这一讲后，你应该能做到：

- 能解释 prompt template 和 workflow 的区别。
- 能把复杂任务拆成 4-7 个步骤。
- 每一步有明确输出。
- 至少有 2 个人工确认点。
- 有最终验收标准。
- 这个 workflow 下次还可以复用。
