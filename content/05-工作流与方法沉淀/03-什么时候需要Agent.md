# 什么时候需要 Agent

## 先判断固定流程是否已经够用

Agent 是很多 AI 课程里最容易被提前讲复杂的概念。对入门阶段的读者来说，过早追求 agent，反而会让学习路径跑偏。

这一讲只解决一个问题：什么时候真的需要 agent，什么时候 prompt、template 或 workflow 就够了。

## 先给结论

不是所有 AI 任务都需要 agent。

如果任务路径清楚、步骤固定、材料有限，用 workflow 就够了。

当任务需要 AI 自己观察结果、选择下一步、调用工具、循环推进时，才更接近 agent。

## Agent 不是“更会聊天的 AI”

入门阶段最容易产生的误解是：agent 等于更聪明、更主动、更像人。

更准确的理解是：

```text
Agent 是一个能根据当前状态和环境反馈，在允许的动作中选择下一步，
再把执行结果写回状态并重复运行，直到完成、等待、失败或被人工停止的系统。
```

普通对话更像“一问一答”。Agent 多了一条可重复的“观察—选择—执行—写回”循环。模型通常提出下一步或生成工具参数，真正的读取、写入和发送仍由外部程序执行，并受权限规则约束。

比如：

```text
每天检查指定资料源，如果发现竞品价格更新，就整理变化、标注来源，并提醒负责人确认。
```

这个任务不是一次回答，而是持续观察、判断、行动和记录。

定时触发或重复执行本身不构成 Agent。如果检查范围、条件和动作都已预先定义，一条固定 Workflow 也能完成；关键仍是运行中的结果是否需要模型选择后续动作。

## 四种协作层级

| 层级 | 适合任务 | 例子 |
|---|---|---|
| Prompt | 一次性简单任务 | 改写一段文字 |
| Template | 重复但结构稳定 | 每周会议纪要 |
| Workflow | 步骤与分支可以事先写清 | 按固定顺序完成资料研究简报 |
| Agent | 下一步要根据运行时结果从多个允许动作中选择 | 检查多个来源，并按发现决定继续查哪一项或升级给人 |

这个表帮助读者不要把所有问题都升级成 agent。

## Agent 的基本循环

先认识循环中可执行的动作。Agent 应用可能提供搜索、读取资料、写入文件、运行代码或操作网页等工具；模型根据任务选择动作，外部程序实际执行，再返回原文、文件、数值或错误。是否具备这些能力，取决于当前应用和环境。

例如，制作资料简报时，“搜索”可能只返回候选链接；接下来需要“打开网页”才能取得正文；“写文件”则把整理后的内容保存到具体位置。这三步留下的结果不同，不能把找到链接当作读完材料，也不能把说出文件名当作已经保存。

想先认识 Codex、Claude Code、Manus 等应用，以及它们可能调用的基本能力，可以按需查看[工具地图](../06-工具地图与个人系统/01-按任务类型理解AI工具.md)。

一个 Agent 的运行系统通常会反复经历四步：

```text
观察：读取当前状态和新的工具结果
选择：在允许动作中提出下一步
执行：外部程序校验权限后调用工具
写回：保存结果与状态，决定继续、等待、失败或停止
```

Workflow 的步骤与分支通常由人预先定义；Agent 会在运行中根据结果选择下一步。这样的灵活性增加了需要检查的路径；实际风险还取决于工具能做什么、任务影响多大，以及有没有适当的检查。

## Agent 的必要条件

是否值得引入 Agent，可以先过四道门：

1. **路径门**：下一步确实要根据运行时结果选择，而不是一张固定流程图就能写完。
2. **反馈门**：每次动作都能得到可观察结果，并写回明确状态。
3. **验证门**：中间结果和最终结果能够被规则、证据或人检查。
4. **控制门**：工具权限、预算、停止、失败和恢复条件已经定义。

路径门不通过，优先使用 Workflow；后三道任一道不通过，都不应把自主循环放进真实高影响环境。

进入严肃工作前，还要确认：

- 过程、来源和版本能记录；
- 失败能被 Eval 覆盖；
- 出错时有回退或人工接管方式。

如果一个 agent 做完后没人知道它看了什么、为什么这么做、哪里可能错，就不适合用于严肃工作。

## 例子：资料研究是否需要 Agent

### 不需要 Agent 的版本

你已经有材料，只需要整理成研究简报。

用 workflow：

```text
整理事实 -> 做推断 -> 拆流程 -> 生成简报 -> 人工验收
```

这不需要 agent。

### 可能需要 Agent 的版本

你希望 AI 每周自动：

- 检查指定网站和资料源。
- 识别更新。
- 摘要变化。
- 判断哪些内容影响当前项目。
- 生成周报。
- 遇到高风险信息时提醒人确认。

这个任务有持续目标、外部工具、循环和判断，才开始接近 agent。

## Agent 的风险

Agent 的风险不是“它会变聪明”，而是错误会被放大。

常见风险：

- 目标不清，越跑越偏。
- 工具权限过大。
- 中间错误没有被发现。
- 把未核查信息继续传递。
- 没有停止条件。

所以 agent 比 prompt 更需要边界、日志和 eval。

## Agent 需要什么控制系统

可以把 agent 的控制要求拆成六项：

| 控制项 | 要解决的问题 |
|---|---|
| 目标 | 它持续负责什么，不负责什么 |
| 工具 | 它能读取、搜索、写入或调用什么 |
| 权限 | 哪些动作能自动做，哪些必须等待确认 |
| 状态 | 当前任务进展、已用资料、待确认事项 |
| 日志 | 每次判断和行动的依据是什么 |
| Eval | 如何用固定样例或标准判断它是否可靠 |

没有这些控制，agent 很容易变成“自动化地犯错”。

## Agent 和 Harness 的区别

你在应用里看到的 Agent，一般已经组合了模型、工具和运行循环。**Harness 是组织这一过程的运行支撑**：把工具结果交回模型，准备后续上下文，管理进度，并按配置检查权限、验证结果、停止或恢复。

```text
Agent 的动作选择：材料不够，下一步补查哪一份？
工具执行：读取选定材料，返回正文或错误。
Harness 的运行支撑：把结果交回下一轮，记录进度，组织检查与继续或停止。
```

例如，简报写到一半中断，支持恢复的运行环境会根据已保存的进度和文件继续处理，而不是要求你重新解释全部过程。保存聊天记录本身未必足以做到这一点，还需要明确任务状态和恢复方式。

Harness 的术语范围因项目而异，不是一个必须单独安装的统一软件，也不等同于更强的模型。本课采用“运行支撑”的口径。可进入[进阶第一节：从 Prompt 到 Harness](../09-Agent与Harness工程/01-从Prompt到Harness工程.md)，通过一次文件任务进一步理解。

## Agent 任务说明卡

如果你真的要设计 agent，至少写清：

```text
目标：
它持续负责什么任务？

可用工具：
它能读什么、写什么、调用什么？

行动边界：
哪些动作不能自动执行？

人工确认点：
什么时候必须停下来问人？

停止条件：
什么时候任务完成？

日志要求：
它要记录哪些判断和来源？

评估方式：
如何判断它做得对？
```

可以再补一项：

```text
升级规则：
遇到什么情况必须停止自动执行，并交给人判断？
```

常见升级规则包括：

- 找到相互冲突的来源。
- 涉及客户承诺、价格、合同、合规或对外发布。
- 达到预先设置的重试、轮次、时间或成本上限。
- 工具返回结果异常。
- 任务超出原定范围。

### 教学反馈

如果理由只是“这个任务比较复杂”，还不足以使用 Agent。请指出哪一个中间结果会改变下一步，以及系统怎样观察、验证和停止。

如果路径固定、每一步都能预先写清，优先选择 Workflow；更少的自主性通常意味着更容易检查和恢复。

## 验收标准

完成这一讲后，你应该能做到：

- 不再把所有 AI 任务都叫 agent。
- 能区分 prompt、template、workflow、agent。
- 能判断一个任务是否需要工具和循环。
- 能写出 agent 的边界和停止条件。
- 知道入门阶段应先把 workflow 做稳定，再考虑 agent。
