# 把有效方法变成可复用的 Skill，而不是收藏一条 Prompt

你曾经用半天把一项资料研究任务做得很好。一个月后，类似任务再次出现，你只找到了当时最后一条 prompt，却忘了材料怎样筛选、哪一步出过错、最终改了哪些地方。

保存一句话，只保存了交互的表面；能复用的能力还需要适用边界、输入、过程、工具、验收和失败处理。

> 本课程里的 Skill，指一份面向特定任务、可被再次执行和验证的能力说明。它把已验证的方法、所需材料与工具、输出合同和安全边界封装在一起。

Skill 不是行业里唯一的技术格式。不同产品可能用不同文件或机制实现；这一讲先建立不依赖工具的内容合同。

## Prompt、Template、Workflow 和 Skill 的边界

| 资产 | 主要解决什么 | 最小内容 |
|---|---|---|
| Prompt | 完成一次交互 | 当前请求和必要条件 |
| Template | 让同类输入使用稳定结构 | 固定说明、变量和输出格式 |
| Workflow | 让多步骤任务按状态推进 | 步骤、检查点、异常和人工门 |
| Skill | 让一种能力在合适场景被安全复用 | 触发、输入、流程、工具/资产、验证、边界、版本 |

Skill 可以包含 Prompt、Template 和 Workflow，但不是把它们换一个文件夹名称。判断是否已成为 Skill，要看另一位执行者能否在不翻原聊天记录的情况下回答：什么时候用、需要什么、怎样运行、什么算完成、失败时怎么办。

## 一个最小 Skill 要写清八件事

```text
名称与目的：解决哪类具体任务？
适用 / 不适用：什么情况下调用，什么情况下不要调用？
必需输入：缺少什么就不能开始？
输出合同：交付物、字段、位置和格式是什么？
执行方法：关键步骤、顺序与检查点是什么？
工具与资产：需要哪些模板、参考资料或工具，权限到哪里？
验证与失败：怎样验收，哪些情况必须停止或升级？
责任与版本：谁维护、为什么修改、用哪些案例验证过？
```

并不是每一项都要写成长文。简单任务可以一页完成；但删除任意字段后，如果执行者会误用或无法验收，就说明它仍是必要内容。

## 示例：资料研究简报 Skill

```text
名称：内部资料研究简报
目的：把给定内部材料整理成支持一次讨论的一页简报。

适用：
- 已有明确研究问题和可用材料；
- 结果用于内部讨论，负责人会核查后再采用。

不适用：
- 要求自动给出法律、投资或人事结论；
- 没有材料却要求具体市场数字；
- 需要未经确认直接对外发布。

必需输入：
- 研究问题、目标读者、待支持的决定；
- 材料清单、来源、日期与版本；
- 禁止推断项和验收标准。

执行方法：
1. 盘点材料并标记版本、冲突和缺失；
2. 提取可回溯事实；
3. 把推断与事实分开；
4. 形成支持当前决定的一页简报；
5. 核查主张、风险和待确认项。

输出合同：
- 研究问题、关键事实、有限推断、建议动作、风险、待补资料；
- 关键主张附材料位置。

停止 / 升级：
- 来源冲突且无法判断当前版本；
- 关键问题没有材料支持；
- 内容涉及对外承诺或专业结论。

验证：
- 事实和推断分开；
- 未知项没有被补齐；
- 建议回应原定决定；
- 用标准、缺失和冲突案例回归。

版本：v0.3；维护人：研究负责人；
本次修改：新增冲突来源处理，来自案例 R-017。
```

这份 Skill 不保证任何研究都自动正确。它定义了一个有限能力：在什么条件下，以什么证据和边界，重复完成哪类工作。

## 案例库不是优秀作品展

如果案例库只保存最终成品，就很难知道方法为什么有效。一个有学习价值的案例至少保留：

| 记录 | 要留下什么 |
|---|---|
| 原始情境 | 真实目标、材料和限制 |
| 使用版本 | 当时用的任务卡、Skill、模型或工具版本 |
| 运行证据 | 关键中间产物、来源和人工门 |
| 失败与修改 | 哪一步出错，人工怎样修正 |
| 最终结果 | 采用、降级、放弃或仍待确认 |
| 回流决定 | 应修改哪项资产，是否加入 Eval |

成功案例说明能力上限，失败案例暴露边界，边界案例决定什么时候必须停。三类都要保存，Skill 才不会只对最顺利的输入有效。

## 把真实失败回流到正确资产

一次失败不一定要改 Skill 主说明。先定位它属于哪一层：

| 失败 | 应优先更新 |
|---|---|
| 任务用途经常说不清 | 任务卡或触发说明 |
| 总是漏某个输出字段 | Template 或输出验证 |
| 资料版本经常混用 | 上下文选择和材料索引 |
| 步骤顺序导致返工 | Workflow |
| 工具越权或错误写入 | 权限规则和 Harness |
| 某类输入反复失败 | Eval 集与适用边界 |

如果每次失败都只往主 prompt 里加一句，资产会越来越长，却仍无法说明哪里真正受控。

## 版本要说明“为什么变”，不只写一个编号

版本记录可以很轻：

```text
v0.2
- 发现：材料缺负责人时，输出会自行补齐。
- 修改：输出合同增加“未知写待确认”。
- 验证：重跑旧标准案例和新缺失案例。
- 结果：两类通过；冲突来源仍会误判。
- 已知限制：来源冲突时必须交给人。
```

下一版只有在修复新失败、且旧通过案例没有明显退化后，才替换当前版。文件存在不代表能力成熟，真实运行和回归证据才是版本升级的依据。

## 个人工作台不需要一开始做成平台

用普通文件夹就可以起步：

```text
AI能力工作台/
├── skills/          # 当前可用能力说明
├── templates/       # 任务卡、输出结构和检查表
├── cases/           # 成功、失败和边界案例
├── evals/           # 固定样例与评分记录
├── references/      # 有来源和版本的参考材料
└── changelog.md     # 当前版本和修改原因
```

重要的不是目录名称，而是三条维护规则：

1. 当前可用版本只有一个清楚入口，旧版不和现版混用；
2. 案例能回到当时使用的资产版本；
3. 失败会进入边界、流程或 Eval，而不是只留在聊天记录里。

当多人开始复用时，再补负责人、访问权限、发布状态、敏感数据处理和停用规则。个人经验进入团队共享前，还要脱敏并删除只对原场景成立的隐含假设。

## 怎样判断一项方法值得沉淀

不是每次成功都要做成 Skill。优先选择：

- 会重复发生，且每次临场重做成本明显；
- 输入和输出能够描述；
- 人能验收关键结果；
- 已经出现至少一次可解释的成功或失败；
- 复用不会把高风险决定偷偷自动化。

如果任务仍在探索、目标频繁改变，先保存案例和复盘即可。等稳定部分出现后，再封装最小 Skill。

### 把一个收藏 Prompt 升级成 Skill 草稿

选择一条你曾经复用过的 prompt，补齐下面内容：

1. 适用与不适用场景；
2. 必需输入和缺失时的停止条件；
3. 输出合同；
4. 执行步骤与人工门；
5. 一个成功案例、一个失败或边界案例；
6. 验收方式、维护人和当前版本。

然后把原聊天记录移出“必需依赖”：如果不看那段对话仍然可以执行和验收，才算形成可复用草稿。

### 教学反馈

如果你的 Skill 只有一段说明文字和一条 prompt，优先补“什么时候不要用”和“怎样证明完成”。这两项最能暴露它是否只是收藏。

如果案例只有最终成品，再补原始任务、所用版本、人工修改和失败原因；否则案例不能支持下一次改进。
