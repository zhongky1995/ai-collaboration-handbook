# 轻量 Eval：验证一套方法，而不是给一次回答打感觉分

同一个会议纪要提示词，第一次遇到记录清楚的周会，结果很好；第二次遇到多人插话、决定未确认、负责人缺失的记录，它却把讨论写成结论，还补出了截止时间。

哪一次代表真实水平？只看任意一份都回答不了。

> Eval 是在预先约定的任务范围内，用一组有代表性的输入、明确的通过条件和失败记录，检查某个 AI 方法是否达到使用要求。

这里被评估的不是抽象的“AI 聪不聪明”，而是一个可指认的版本：某个任务说明、上下文包、模板、Workflow、模型与配置的组合。组合发生变化，就需要说明这是哪个新版本。

## Eval 和三种常见检查有什么不同

| 检查 | 回答的问题 | 例子 |
|---|---|---|
| 单次验收 | 这一次结果能不能用？ | 这份纪要有没有漏掉本次会议结论 |
| 事实核查 | 某条主张是否被可靠来源支持？ | 负责人是否真的在原记录中被指定 |
| Eval | 这套方法在预定的一组情况中是否稳定达到要求？ | 换成缺失、冲突和混乱记录后是否仍不乱补 |

三者会互相使用，但不能替代。Eval 里可以包含“来源忠实”评分；一次通过来源核查，也不能证明方法换材料后仍然可靠。

## 轻量，不等于随便

轻量 Eval 不要求先搭自动化平台。一张表、几份经过脱敏的真实样例和一份版本记录就能开始。但它至少要有六个组成部分：

1. **评估对象**：明确要测试的提示词、模板或流程版本；
2. **使用范围**：它准备给谁，在什么任务和风险条件下使用；
3. **样例集**：覆盖正常情况和已知失败面；
4. **评分与硬失败**：什么可以按程度评分，什么出现一次就不能通过；
5. **运行记录**：输入、输出、配置、评分和失败证据；
6. **发布决定**：继续试用、限制范围、修改重测，还是停止使用。

少了使用范围，“通过”没有边界；少了硬失败，平均分可能掩盖一次严重错误；少了版本，下一次也不知道测的是不是同一套方法。

## 样例不是越多越好，要覆盖真实失败面

第一次可以从少量样例开始，数量根据任务差异和风险决定，不存在所有任务通用的“3–5 个就够”。会议纪要至少要考虑这些切片：

| 样例切片 | 主要测试什么 |
|---|---|
| 标准记录 | 正常输入能否得到完整结构 |
| 多人混乱记录 | 是否混淆说话人、讨论与决定 |
| 关键字段缺失 | 是否擅自补负责人、日期或数字 |
| 来源冲突 | 是否保留冲突，而不是自行选择 |
| 权限诱导 | 是否在未批准时发送或更新正式系统 |

如果一种失败在真实工作里出现过，就把对应输入保存为回归样例。以后每次修改都重跑它，避免修好新问题却让旧问题回来。

样例还要保护隐私：脱敏不影响任务判断的个人信息，并记录哪些字段不能进入测试或日志。

## 先写通过条件，再看输出

看到答案后再定标准，人很容易把标准迁就到当前结果。应在运行前写清评分维度、评分依据和硬失败。

下面是一份**教学示例**，不是行业通用量表：

| 维度 | 0：失败 | 1：部分达到 | 2：达到本次要求 |
|---|---|---|---|
| 决定忠实 | 把讨论写成决定 | 有少量状态混淆 | 决定、建议、待确认分开 |
| 行动项 | 漏项或编造 | 提取基本正确但字段状态不清 | 动作准确，缺失字段明确待确认 |
| 证据位置 | 关键内容无法回到记录 | 部分有位置 | 关键决定与行动项均可定位 |
| 输出结构 | 无法按团队流程使用 | 需要明显重排 | 字段和顺序符合约定 |

可以评分的维度反映质量程度；硬失败则表示某个边界不能被总分抵消。例如：

- 编造负责人、日期或金额；
- 把明确未通过的建议写成正式决定；
- 未经批准对外发送；
- 泄露不应进入输出的敏感信息。

即使其他维度得分很高，只要出现约定的硬失败，本次版本也不能按原范围发布。

## 通过线是本地决定，不是神奇数字

“平均 8 分以上”“五个样例通过”只有在量表、风险和用途已经定义后才有意义。不同任务需要不同发布条件：

- 个人学习摘要可以允许较多人工修改；
- 团队纪要对负责人和决定状态更敏感；
- 客户发送或正式系统写入应有严格权限硬失败。

因此，通过线应该写成可解释的本地规则：

```text
适用范围：内部项目周会纪要草稿，不自动发送。
质量条件：所有样例的决定状态和行动项达到团队最低要求。
硬失败：不得编造负责人 / 日期；不得把草稿写入正式会议系统。
人工门：会议主持人核对后才能分发。
已知限制：多人同时发言且记录无说话人标识时，只整理主题，不归因到个人。
```

这比一个脱离用途的总分更能指导真实使用。

## 跑完以后，先定位失败发生在哪一层

Eval 的目的不是宣布“模型不行”，而是找到应该改什么。

| 失败证据 | 更可能的问题层 | 优先修改 |
|---|---|---|
| 用途和读者总被误解 | 任务说明 | 重写目标、读者和输出 |
| 关键记录没有进入回答 | 上下文 | 检查材料选择、版本或检索 |
| 同类字段反复漏掉 | 模板 / 结构 | 固定字段并加验证 |
| 讨论与决定顺序混乱 | Workflow | 先分状态，再生成成品 |
| 工具越权或重复执行 | 权限 / 状态 | 增加硬门、幂等与停止规则 |
| 只在某模型版本退化 | 模型 / 配置 | 同样例对照并决定是否回退 |

如果失败原因不清，先保存证据，不要立刻把 prompt 加长。一个输出错误可能源于材料没取到、规则没生效、工具结果被截断或模型生成偏差，修错层会让系统更复杂却不更可靠。

## 比较新旧版本，要控制比较条件

想知道修改是否有效，至少要做到：

1. 用同一批样例比较旧版和新版；
2. 保持模型、工具与关键配置一致，或明确记录差异；
3. 逐个样例看改善和退化，不只看平均分；
4. 生成有随机性时，对关键样例重复运行并记录波动；
5. 同时记录质量、人工修改量、成本和时间。

“新版这一次高两分”不自动等于真实改善。若分差落在运行波动内，或质量提升同时带来新的硬失败，就不能据此升级。

## Workflow 和 Agent 还要检查过程

只生成文本的提示词，重点往往是输入和输出。Workflow 或 Agent 还会读写状态、调用工具和执行动作，所以 Eval 必须同时看运行轨迹。

| 检查层 | 要观察什么 |
|---|---|
| 输出 | 事实、结构、用途、未知项是否达标 |
| 过程 | 是否选对来源、按步骤推进、正确处理工具失败 |
| 权限 | 是否在应确认时停下，有没有越权动作 |
| 状态 | 是否重复、跳步、丢失进度或无法恢复 |
| 交接 | 下一执行者是否得到目标、证据、风险和产物位置 |

这也是为什么“最终文案看起来不错”仍可能不通过：如果系统曾读取越界数据、未经确认发送，或只是碰巧在多次重试后成功，过程并不可靠。

## 一张最小运行记录

```text
评估对象与版本：
适用范围：
模型 / 工具 / 关键配置：
样例编号与切片：

输出评分：
硬失败：有 / 无；证据：
关键过程事件：
人工修改：
成本与时间：

失败类型：
应修改的资产：
是否加入回归集：
发布决定与限制：
```

当一次真实失败被保存成样例、定位到正确层、修复后重跑旧样例，经验才从“下次注意”变成了可验证的方法。

### 为一个常用任务建立最小 Eval

选择一个你准备重复使用的任务，先写适用范围和评估对象版本。准备覆盖正常、缺失和一种高风险失败面的样例，然后定义：

- 两到四个能从输出中观察的评分维度；
- 至少一个不能被平均分抵消的硬失败；
- 人工确认点；
- 新旧版本怎样用同一组样例比较。

运行一次后，不要先改 prompt。先把每个失败定位到任务、上下文、模板、Workflow、权限或模型中的一层。

### 教学反馈

如果你的通过条件只有“平均分达到某个数字”，请补充适用范围和硬失败。数字不能说明哪一种错误绝不允许发生。

如果失败记录只有“效果不好”，继续记录具体证据：哪条输入触发了什么错误，它违反了哪项标准，应该修改哪一层。
