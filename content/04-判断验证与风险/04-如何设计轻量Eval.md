## 最小 Eval 怎样既便宜又能发现关键失败？

轻量 Eval 从固定任务、可观察评分项和失败样本开始；结果看起来好但轨迹越权，整体仍不能通过。

### 在固定研究简报中操作

给研究简报设置事实对应、决策相关、风险披露三项 0/1/2 评分，并补一条工具越权的轨迹级失败。

### 在「如何设计轻量 Eval」中最容易犯的错

只评分文风会漏掉事实错误和轨迹越权；只看总分又无法知道应该改哪一层。

### 「工作流」应留下什么证据

- **结构检查**：固定样例包含结果级评分、轨迹级禁止项和失败归因。
- **固定案例对照**：说明这次修改解决了哪一种失败，并保存进「工作流」。
- **需人工核验**：事实、业务适用性与高风险决定仍由人负责。

本页为主脊柱增加 **步骤、状态、检查点、人工门与异常分支**；满足以上证据后，回到作品继续推进 Agent Loop：只把动态分支交给循环。

## 深入理解与原有知识

## 这一讲解决什么问题

很多人判断 AI 好不好，只看一次输出。如果这次看起来不错，就认为 prompt 好；如果这次不理想，就认为模型不行。

这不够。真正要把 AI 用进工作，需要知道一个方法是否稳定。

Eval 的作用，就是把“感觉不错”变成“可以测试、比较和改进”。

## 先说 Eval 是什么

Eval 是 evaluation 的缩写，可以理解成“评估、测试、打分”。

在 AI 协作里，Eval 不是考试模型有多聪明，而是检查一个 AI 用法是否稳定。它通常回答三个问题：

1. 同一个 prompt 遇到不同材料时，结果是否仍然可用？
2. 同一个 workflow 换一个案例后，关键步骤是否还有效？
3. AI 输出是否达到你提前定义的质量标准？

例如你写了一个会议纪要 prompt。它第一次生成得很好，不代表它真的可靠。你还要看它遇到“结论不明确、负责人缺失、讨论和决策混在一起”的会议记录时，会不会乱补、漏掉或误判。

这个测试过程，就是 Eval。

入门阶段不用把 Eval 想复杂。你可以先把它理解成一张评分表：

```text
固定几个真实样例
固定几个评分维度
每次输出后打分
记录失败原因
再根据失败修改 prompt 或 workflow
```

## Eval 不一定复杂

入门阶段不需要搭建技术平台，也不需要写自动化测试。轻量 Eval 可以只是一张表。

它需要三样东西：

1. 固定样例。
2. 评分维度。
3. 失败记录。

只要能用同一组样例反复测试 prompt 或 workflow，就已经开始做 eval。

## Eval 不是事实核查

Eval 和事实核查有关，但不是一回事。

| 方法 | 主要回答什么问题 |
|---|---|
| 事实核查 | 这条具体结论是不是真的？来源是否可靠？ |
| Eval | 这个 prompt、workflow 或 AI 用法在一组样例上是否稳定？ |

例如你检查一份会议纪要：

- 事实核查看的是：这条结论是否真的来自会议记录。
- Eval 看的是：同一个会议纪要方法遇到不同会议记录时，是否都能区分结论、讨论、待办和待确认。

所以，事实核查解决“这一条对不对”，Eval 解决“这个方法稳不稳”。

## 为什么单次成功不够

假设你写了一个会议纪要 prompt。第一次效果很好，因为会议记录清楚、待办明确、负责人完整。

但第二次会议记录很混乱：

- 很多人插话。
- 结论和建议混在一起。
- 待办没有截止时间。
- 有些任务只是在讨论，没有正式确定。

如果 prompt 在第二种材料下把讨论写成结论，那它就不稳定。

所以 eval 要覆盖不同难度样例。

## 样例怎么选

样例不是随便找几份材料。好的 Eval 样例要覆盖真实使用中的差异。

以会议纪要为例，至少准备这些类型：

| 样例类型 | 为什么需要 |
|---|---|
| 标准样例 | 确认 prompt 能处理正常情况 |
| 混乱样例 | 测试它是否会把讨论写成结论 |
| 信息缺失样例 | 测试它是否会擅自补负责人、时间、数字 |
| 高风险样例 | 测试它是否会标注争议、风险和待确认 |
| 边界样例 | 测试它是否知道什么时候不能下结论 |

如果只用最顺的样例测试，Eval 会给你虚假的稳定感。

## 轻量 Eval 的四步

```text
1. 选 3-5 个真实样例
2. 定义 5 个评分维度
3. 每个维度 0-2 分
4. 记录失败原因并改 prompt
```

更完整一点，可以补两项：

```text
5. 设置通过线
6. 下一版修改后用同一组样例重测
```

通过线不是为了追求完美，而是为了决定“这个方法能不能进入日常使用”。

例如：

```text
5 个样例平均 8 分以上；
任一高风险维度不能低于 1 分；
不得出现编造负责人、编造数字、把未确认意见写成结论。
```

## 示例：会议纪要 prompt 的 Eval

### 测试样例

| 样例 | 特点 |
|---|---|
| A | 记录清楚，结论明确 |
| B | 讨论很多，结论不明确 |
| C | 有待办，但负责人缺失 |
| D | 包含争议和未确认信息 |

### 评分表

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 结论准确 | 结论错误 | 部分准确 | 能区分结论和讨论 |
| 待办完整 | 漏掉或编造 | 部分提取 | 动作、负责人、时间清楚 |
| 不确定性 | 擅自补全 | 部分标记 | 缺失信息都标待确认 |
| 格式稳定 | 不按格式 | 部分符合 | 完全符合指定结构 |
| 可用性 | 不能用 | 需要较多修改 | 少量修改可用 |

满分 10 分。连续多个样例达到 8 分以上，才说明这个 prompt 比较稳定。

### 通过线

这个会议纪要 prompt 可以设置这样的通过线：

```text
平均分 >= 8 分
结论准确不得低于 1 分
不确定性不得低于 1 分
不得编造负责人和截止时间
```

如果平均分不错，但出现一次编造负责人，这个 prompt 仍然不能直接进入工作流。因为这类错误会让后续协作产生真实成本。

## 失败记录怎么写

不要只写“效果不好”。要记录失败类型。

| 失败类型 | 例子 | 修改方向 |
|---|---|---|
| 材料误读 | 把建议写成结论 | 要求区分“已确定”和“讨论中” |
| 擅自补全 | 补了负责人 | 增加“不明确写待确认” |
| 格式漂移 | 输出变成散文 | 强化输出表格 |
| 重点遗漏 | 漏掉风险 | 增加风险检查步骤 |
| 表达不适配 | 太正式或太口语 | 补目标读者和语气 |

失败记录是改进 prompt 的依据。

## 怎么根据 Eval 改方法

Eval 的目的不是打分本身，而是定位应该改哪里。

| 失败集中出现在哪里 | 优先改什么 |
|---|---|
| 多个样例都漏掉同一类信息 | 改输出结构或检查清单 |
| 只在材料混乱时失败 | 增加“先整理事实、再生成”的步骤 |
| 经常擅自补全 | 加强边界：未知写待确认 |
| 格式经常漂移 | 把格式拆成表格、字段和示例 |
| 高风险内容处理不好 | 增加人工确认点，不要让 AI 自动发布 |

如果修改 prompt 仍然不稳定，说明问题可能不在一句提示词，而在 workflow。此时应该把任务拆成多个步骤，而不是继续加长 prompt。

## 从输出 Eval 到 Agent Eval

本讲的评分表主要检查最终输出。Agent 还会调用工具、更新状态、交接任务和执行外部动作，因此还要检查运行过程：

| 新增检查 | 要回答的问题 |
|---|---|
| 工具轨迹 | 是否选对工具、使用正确参数和来源？ |
| 权限 | 是否在该确认时停下，是否出现越权？ |
| 状态 | 是否重复、跳步或丢失当前进度？ |
| Handoff | 下一位执行者是否收到目标、证据、风险和产物位置？ |
| 终止 | 是否在完成、受阻或超限时正确结束？ |

所以，Agent Eval 需要把“最终答案评分”和“关键运行事件”结合起来。详细方法见 [Eval、可观测性与持续改进](../09-Agent与Harness工程/07-Eval可观测性与持续改进.md)。

## Prompt 改进示例

原 prompt：

```text
请根据会议记录生成会议纪要，包含结论和待办。
```

发现失败：AI 经常把讨论中的建议写成确定结论。

改进：

```text
请根据会议记录生成会议纪要。

特别要求：
- 只把明确达成一致的内容写入“会议结论”。
- 对于有人提出但未确认的建议，放入“待确认问题”。
- 如果负责人或截止时间不明确，不要补全，写“待确认”。
- 输出后自查：是否把讨论意见误写成结论。
```

这就是 eval 反过来推动 prompt 改进。

## 练习

选择一个你准备长期使用的 AI 任务，例如：

- 会议纪要。
- 长文总结。
- 资料研究。
- PPT 大纲。
- 邮件改写。

准备 3 个真实输入样例，建立评分表，跑同一个 prompt。

输出：

1. 样例说明。
2. 评分表。
3. 每个样例得分。
4. 失败原因。
5. 下一版 prompt 修改点。

## 验收标准

完成这一讲后，你应该能做到：

- 不再用一次输出判断方法好坏。
- 能设计 3-5 个测试样例。
- 能设置 0-2 分评分维度。
- 能记录失败类型。
- 能根据失败修改 prompt 或 workflow。
