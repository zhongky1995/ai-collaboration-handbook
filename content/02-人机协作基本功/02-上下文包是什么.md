## 材料怎样进入任务，而不是堆进提示词？

上下文包不是附件堆，而是任务、材料、规则与样例组成的当前工作集；每一项都应说明用于哪个判断。

### 在固定研究简报中操作

为每份材料写来源、版本、用途；找不到用途的材料先排除，冲突版本不能同时当现状。

### 在「上下文包是什么」中最容易犯的错

材料没有用途标签、冲突版本同时出现、待核查说法进入结论，都会污染当前判断。

### 「模板与上下文材料包」应留下什么证据

- **结构检查**：每项入选材料支持一个判断；排除项、来源和版本都有记录。
- **固定案例对照**：说明这次修改解决了哪一种失败，并保存进「模板与上下文材料包」。
- **需人工核验**：事实、业务适用性与高风险决定仍由人负责。

## 深入理解与原有知识

## 这一讲解决什么问题

很多人知道要“给 AI 上下文”，但不知道上下文到底该给什么。

于是常见做法是：

- 把所有材料一股脑贴进去。
- 只给一句背景。
- 反复在对话后面补充要求。
- 指望 AI 自己知道项目、读者和标准。

结果是：AI 有时抓不到重点，有时忽略关键材料，有时输出一份看似完整但不适合真实场景的内容。

上下文包的作用，就是把 AI 完成任务所需的信息整理成一个清晰输入。

## 上下文包包含什么

一个可用的上下文包通常包括七类信息：

| 信息 | 作用 | 示例 |
|---|---|---|
| 任务目标 | 告诉 AI 这次要完成什么 | 生成一份给项目组讨论的用户反馈摘要 |
| 背景 | 说明为什么现在做 | 项目进入复盘阶段，需要决定下个版本重点 |
| 目标读者 | 决定表达深度和语气 | 产品经理、运营、设计同事 |
| 输入材料 | 限定依据来源 | 用户访谈摘录、客服反馈、数据截图 |
| 术语说明 | 避免误解内部词 | “转化”指提交表单，不是付款 |
| 约束边界 | 避免编造和越界 | 不要补充没有来源的数据 |
| 验收标准 | 定义输出好坏 | 每条结论必须对应原始材料 |

上下文包不是越长越好，而是要让 AI 看见关键判断依据。

## 一个例子

模糊输入：

```text
帮我总结一下用户反馈。
```

上下文包输入：

```text
任务目标：
请把下面用户反馈整理成产品复盘材料，帮助项目组判断下个版本优先修什么。

背景：
我们刚上线了新版注册流程，目前收到了客服记录和用户访谈摘录。团队争议点是：问题主要出在页面理解、表单字段，还是短信验证码。

目标读者：
产品经理、设计和运营同事。他们了解项目背景，但没有完整看过反馈原文。

输入材料：
下面是 15 条用户反馈。请只基于这些材料整理。

术语说明：
“提交失败”指用户点击提交后没有成功进入下一步，不一定是系统报错。

约束边界：
不要推断真实用户比例，不要补充没有来源的数据。

输出格式：
请输出表格：问题类型 / 反馈依据 / 可能影响 / 建议下一步确认。

验收标准：
每个问题类型至少对应 2 条原始反馈；不足 2 条时标记为“证据不足”。
```

这时 AI 不只是“总结”，而是在一个具体任务中整理材料。

## 上下文包和 prompt 的区别

Prompt 是一次任务说明。上下文包是支撑任务说明的材料和背景。

可以这样理解：

```text
prompt = 我要你做什么
context = 你需要依据什么来做
```

很多 prompt 看起来写得很完整，但如果 context 不足，AI 还是只能靠猜。

## 如何控制上下文数量

上下文太少，AI 会泛；上下文太多，AI 可能抓不住重点。

可以按三层给：

1. **任务摘要**：先说明目标、读者、输出。
2. **关键材料**：给最相关的资料，并标注类型。
3. **补充材料**：让 AI 在需要时再看，或分轮处理。

如果材料很多，不要直接要求 AI “全部总结”。可以先让它分类：

```text
请先把材料按主题分类，并指出每类材料能支持什么判断。
不要先写结论。
```

## 常见失败

| 失败表现 | 原因 | 修正方式 |
|---|---|---|
| 输出很泛 | 只有任务，没有背景 | 补充使用目的和读者 |
| 输出遗漏重点 | 材料没有标注优先级 | 告诉 AI 哪些材料最重要 |
| 输出编造数据 | 没有限定依据 | 明确“只基于材料，不补数字” |
| 输出不适合发送 | 没有目标读者 | 补充接收者和关系场景 |
| 长对话后跑偏 | 上下文分散 | 让 AI 复述当前任务和约束 |

## 验收标准

完成这一讲后，你应该能做到：

- 说清 prompt 和 context 的区别。
- 为真实任务整理上下文包。
- 知道什么时候要分批给材料。
- 在长任务中主动刷新任务目标和约束。
