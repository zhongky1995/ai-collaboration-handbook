## 同一个资料研究简报怎样留下六段证据

下面不是要照抄的答案，而是帮助你识别每一阶段新增的控制。

### 1. Prompt 任务卡：先让任务可验收

原始请求是“帮我研究一下 AI 会议纪要”。任务卡把它改成：给团队负责人一页内部简报，用于决定是否进行两周试行；结论必须标注材料来源，未知说法不得进入结论，最终发布由负责人决定。

**关键证据**：使用者、决定、材料范围、输出形态、三条验收、人类责任。任务适合性判断作为前置附件，说明 AI 可整理材料和生成候选，但不能替负责人做试行决定。

### 2. Context 材料包：只保留支持当前决定的材料

当前流程、同事反馈、试行约束和负责人决策标准进入上下文；过期流程、重复反馈和视觉指南被排除。待核查工具说法单独标记，不能伪装成事实。

**关键证据**：材料 ID、来源、版本、预算、排除理由和冲突记录。事实核查从材料状态开始，而不是写完结论后才补来源。

### 3. Workflow：让长任务停在可恢复的位置

研究简报按 `received → extracting → comparing → drafting → verifying → ready_for_review → done` 推进。每个状态留下提取表、比较表、草稿或核查记录；来源冲突进入独立状态，发送之前保留人工门。

**关键证据**：开始与完成条件、每个状态的产物、检查点、人工门、异常与恢复。

### 4. Agent 运行卡：环境变化时才动态选择

当负责人决策标准缺失时，正确行动是请求人工补充并保存等待状态，而不是按常识猜测或原样重试。工具结果写回状态，下一轮能看到新信息。

**关键证据**：观察、行动理由、工具结果、状态变化、停止原因、重试上限和恢复点。

### 5. 最小 Harness：结果与轨迹一起验收

本地只读材料可 `allow`；外部查询设为 `ask`；发送结果必须 `ask` 或 `deny`。Eval 同时检查“结论是否有材料证据”和“是否未经人工确认就发送”。

**关键证据**：权限矩阵、标准/缺失/冲突三类样例、Trace、Eval、异常关闭、预算和人类升级点。结果正确但轨迹越权，仍然不通过。

### 6. Skill / AgentOS 能力资产包：让方法可交接

通过的六阶段证据被登记为一个有 Owner、版本、适用边界、Handoff、Eval 基线和共享边界的能力包。下一位执行者不看原聊天，也能知道当前状态、下一动作和失败时找谁。

**关键证据**：资产清单、Registry 位置、版本差异、已知失败、回归结果和下一次复用任务。

## 三类反馈怎样落到修改动作

| 反馈类型 | 能证明什么 | 不能证明什么 | 例子 | 应回到哪里改 |
|---|---|---|---|---|
| 结构检查 | 字段、数量、格式或状态满足明确规则 | 事实真实、业务判断正确 | 缺少三条验收条件 | Prompt 的验收字段 |
| 固定案例对照 | 在课程给定材料和答案边界内选择合理 | 真实组织也应使用同一规则 | 外部查询应为 `ask` | Harness 权限矩阵 |
| 需人工核验 | 提醒必须由人承担的判断 | 不会替人给出最终结论 | 试行风险能否接受 | 负责人和人工门 |

一次有效反馈至少包含：`criterionId`、满足/未满足、证据位置、为什么、怎么改、反馈类型、检查时间和责任人。只说“再优化一下”不能形成下一版。

## 按真实任务找迁移练习

| 真实任务 | 推荐起点 | 可保存的辅助证据 | 仍归入哪份正式作品 |
|---|---|---|---|
| 长文总结 | Prompt / Context | 读者用途、取舍依据、遗漏核查 | 任务卡与材料包 |
| 会议纪要 | Workflow | 决策、行动项、待确认项和负责人记录 | Workflow |
| PPT 大纲 | Prompt / Workflow | 页面任务、论证顺序、人工审稿 | 任务卡与 Workflow |
| 工作通知或方案 | Prompt / Harness | 承诺边界、敏感信息、发布前检查 | 任务卡与最小 Harness |
| AIGC 创作 | Prompt / Harness | 视觉 brief、素材角色、候选比较、版权和品牌检查 | 任务卡与最小 Harness |
| 多来源研究 | Context / Agent | 事实表、推断表、来源冲突与缺失材料 | 材料包与 Agent 运行卡 |
| 重复性资料检查 | Workflow / Harness | 状态表、权限、失败样例和恢复记录 | Workflow 与最小 Harness |

AI 任务判断、事实核查、场景产出和 AIGC 发布检查都在这里作为前置判断或辅助证据保留；它们不能替代六阶段作品，也不会单独改变进度。

## 多案例后才判断是否值得沉淀

同类任务积累到三次以上，再使用下表找稳定规律；样例太少时继续保留案例，不要急着封装自动化。

| 案例 / 版本 | 稳定输入 | 稳定状态 | 重复失败 | 人工检查点 | 可新增 Eval | 下一次复用 |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |

如果路径大体固定，把稳定部分升级为 Workflow；如果下一步确实依赖环境反馈，再设计 Agent Loop；如果运行暴露权限、Trace、Eval、异常或预算问题，补最小 Harness；只有别人能接手和回归时，才进入 Skill / AgentOS 能力资产包。

## 复盘通过的最低标准

- 能说清失败属于目标、Context、状态、工具、权限、Eval、Handoff 中的哪一层。
- 待修改项指向具体字段或规则，有 Owner，而不是“提示词不够好”。
- `passed` 有 required 证据；`needs_revision` 有原因和修改动作；没有待修改项时明确写“无”。
- 新版本说明解决了哪个失败，并用旧样例回归，旧证据没有被覆盖。
- 写明下一次在哪个真实任务复用，而不是只说“以后继续学习”。
