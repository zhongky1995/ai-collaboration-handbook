# 用 AI 做一个资料核查面板

写简报前，你需要逐条看材料、区分证据与想法、保留尚未确认的冲突。你可以把这些动作做成一个小页面，试试任务卡和反馈方法怎样用于制作工具。

这是**可选案例实验室**。建议先读[任务卡](../02-人机协作基本功/01-把模糊问题变成AI能执行的任务.md)、[上下文包](../02-人机协作基本功/02-上下文包是什么.md)和[反馈迭代](../02-人机协作基本功/04-示例反馈和迭代.md)。你可以只看案例，也可以使用能生成文件的 AI 编程工具跟做；不影响核心课的继续阅读。

## 任务合同

| 项目 | 本次练习 |
|---|---|
| 使用者与用途 | 简报撰写者，希望带走一份可追溯的材料判断记录 |
| 输入 | 下方三条虚构教学材料，以及使用者填写的状态和依据 |
| 操作 | 看原文 → 人工判断 → 写明依据 → 导出记录 → 检查结果 |
| 产出 | 一页任务说明、可打开的面板、导出的记录、一次修改说明 |
| 完成标准 | 原文可查、未处理项可见、遗漏有提示、导出与填写一致 |
| 人类责任 | 判断材料能支持什么，核查导出结果，决定是否迁移到真实工作 |

[打开资料核查面板示例](../../assets/demos/evidence-panel.html)

示例可以离线使用。它只提供固定教学材料和表单，不调用模型、不自动核查事实。先自己填写并导出一次，再回来看它怎样被定义。

## 第一步：从一个小问题确定范围

本次教学假设是：撰写者需要在整理简报前看清哪些材料可用、哪些仍有疑问。真实工作中要先核对这个问题是否发生过；可以使用[需求证据卡](../08-练习册与案例库/02-可复制作品模板.md)，记录现有做法和具体返工。

为了练习，先只做一条完整路径：三条材料固定展示，使用者人工选择状态、填写依据，然后下载文本记录。账号、联网检索、自动判断和团队协作暂缓。这样你能先判断操作是否清楚，而不必同时处理很多依赖。

“原型”指用于检查方案的小版本。它可以用固定材料验证页面操作，但不能因此宣称已经能处理任意业务资料。

## 第二步：准备可逐条核对的输入

**以下材料全部为虚构教学样例，不代表真实用户或调研结果。**

| 编号 | 材料原文 |
|---|---|
| E01 | 某次内部活动反馈称，提交给负责人前曾重新核对资料出处。 |
| E02 | 一条想法记录称，希望简报能自动检查所有事实。 |
| E03 | 两份说明对同一材料的使用范围描述不同，尚无负责人确认。 |

先不要让 AI 替你判定。三条都应以“未处理”开始；填写后仍能看到原文，方便检查自己的判断是否超出了材料。

## 第三步：把六格任务卡变成页面要求

这一阶段要把需求变成一个实际文件。下面按不同工具共同的动作说明；入口名称和生成速度可能不同，不影响你核对文件与页面结果。

### 先准备一个清楚的工作位置

**做什么：**如果使用能直接读写电脑文件的 Agent 应用，先在电脑上新建一个“资料核查练习”文件夹，再通过应用的“打开文件夹”“选择项目”或类似入口选中它。若使用云端任务环境，就新建一个任务，稍后通过下载取回文件。纯对话工具可以先在新对话中生成代码。

**可能看到什么：**本地文件列表、云端任务文件区，或只有聊天输入区。它们决定了最后从哪里取文件。

**怎样继续：**本地应用先核对所选文件夹；云端应用确认当前任务；纯对话工具按下方“只返回代码”的路径保存。将三条材料的编号和原文连同任务说明一起提交，不只发送课程链接。

### 提交页面要求

把下面内容复制到同一任务，再接上 E01、E02、E03 的完整材料：

```text
请制作一个可在本地浏览器打开的资料核查面板，交付一个名为 evidence-panel.html 的 HTML 文件。
页面的样式和交互写在这一个文件里，能够直接用浏览器打开，无需安装依赖。
使用者是简报撰写者，要带走一份可追溯的材料判断记录。
只使用我提供的 E01、E02、E03，逐条保留编号和原文。

每条材料需要：
- 状态：未处理、支持有限结论、仅为想法、待确认；初始为未处理。
- 判断依据：由使用者填写，页面不自动补写。

用户可以下载文本记录，包含所有材料的编号、原文、状态和依据。
导出前，如果有未处理材料或空白依据，指出编号和漏项并定位到该字段。
空格不算有效依据；补好后可重新导出，已填内容保持不变。
修改字段后，应能再次导出当前内容。

页面注明：虚构教学材料，状态由使用者填写，不代表事实已核实。
输入只留在当前页面，不写入浏览器存储，不上传，不调用外部服务。
页面明显提示：刷新或关闭会丢失填写内容，请先导出。
用清楚的字段标签，让手机和键盘也能操作。

完成后告诉我打开方式、验收方法，以及第一版尚不支持哪些事情。
```

**可能看到什么：**AI 可能先列计划、直接开始写文件、返回下载附件，或只输出一段代码。工具有时也会等待你确认写入位置。

**怎样继续：**只有计划时，明确要求按这份需求生成文件；需要确认时，核对动作确实是写入本次练习文件夹；若返回了需要安装依赖的多文件项目，请它按本次交付要求整理为可以直接打开的单个 HTML 文件。

### 把生成结果变成实际文件

| 你拿到的结果 | 具体操作 | 这一步完成的证据 |
|---|---|---|
| 工作目录中的文件 | 在应用文件列表或电脑文件夹中找到 `evidence-panel.html` | 实际文件存在，位置是本次练习目录 |
| 可下载的附件 | 选择下载，再到下载文件夹找到该文件 | 有实际下载文件；云端文件已取回到电脑 |
| 一整段 HTML 代码 | 用支持纯文本的编辑器新建文件，复制代码块内部的全部代码，不包含开头和结尾的三个反引号，保存为 `evidence-panel.html` | 文件是纯文本 HTML，名称没有变成 `evidence-panel.html.txt` |

如果代码不完整，先让 AI 补全同一个文件再保存。拿到文件后，复制一份并命名为 `evidence-panel-v1.html`，保留首次生成的版本。

### 打开页面，确认可以开始操作

**做什么：**在电脑文件管理器中找到 `evidence-panel.html`，选择用浏览器打开。若双击进入代码编辑器，就通过“打开方式”选择浏览器。也可以使用工具提供的页面预览；最终仍需保留可独立打开的文件。

**可能看到什么：**正常结果是一页包含三条原文、状态选择、依据输入框和导出入口的页面。白屏、只显示代码、缺少字段或按钮无响应，都说明还需要检查。

**怎样继续：**只显示代码时，先核对文件是不是完整 HTML、有没有误存为文本扩展名；页面空白或缺功能时，把实际现象和目标差异发回同一任务。可以从这一句开始：“我用浏览器打开了生成的文件，实际看到……；预期应看到三条材料和导出入口。请检查文件并修正，说明改了哪里。”修正后重新打开或刷新页面，再进入下一步验收。

## 第四步：先看对照，再检查自己的结果

下面是这三条材料的**教学判断示例**。状态由人选择，依据也需要人核对，面板只检查字段是否填写。

| 编号 | 可用状态 | 依据示例 | 不能据此写出的结论 |
|---|---|---|---|
| E01 | 支持有限结论 | 记录提到这一次重新核对出处；未提供耗时或频率。 | 所有撰写者都在这里浪费大量时间。 |
| E02 | 仅为想法 | 这是对功能的愿望，尚未说明真实经历或已有解决方式。 | 自动事实核查已经得到需求验证。 |
| E03 | 待确认 | 两份说明冲突，需负责人确认适用范围。 | 较新的那份一定有效。 |

输入 E01 的状态与依据后，导出的对应记录应当类似：

```text
编号：E01
原文：某次内部活动反馈称，提交给负责人前曾重新核对资料出处。
状态：支持有限结论
依据：记录提到这一次重新核对出处；未提供耗时或频率。
```

编号和原文来自固定材料；状态和依据来自你的填写。这个对应关系就是检查导出是否正确的标准。

| 检查情况 | 应看到什么 |
|---|---|
| 初次打开，直接导出 | 提示哪些材料未处理，定位到第一个漏项 |
| E02 已选状态，但依据只填空格 | 提示 E02 缺少依据，E01 已填内容保留 |
| 三条全部填写后导出 | 下载文本文件，三条内容与页面一致 |
| 修改 E01 依据后再次导出 | 新文件包含修改后的内容；旧文件仍可用于对照 |
| 刷新页面 | 恢复三条未处理材料；页面始终明确提示刷新前导出 |

再试一个反例：在 E02 的依据中填“这个产品肯定有人买”。面板可能允许导出，因为字段确实非空，但这句话超出了材料。**字段检查通过，只证明记录填全；判断是否有依据仍由人核验。**

## 第五步：围绕一个可复现的问题修改

以下是**假设的修改过程**，不是已经发生的试用记录：

- 第一版：漏填 E02 的依据时，点击导出没有文件，也没有提示。
- 问题卡：记下输入、按钮、期望文件、实际无响应以及可见报错。
- 修改要求：导出前列出漏项并定位；已经填写的内容保留。
- 复测：再次漏填 E02，应看到提示；补齐后能导出；核对 E01、E03 内容未受影响。

具体操作是：回到制作这个文件的同一任务，发送下面的反馈，然后再次打开修正版检查。

```text
我已填写 E01、E03 的状态和依据，并选择 E02 的状态，但没有填 E02 的依据。
点击导出后，实际没有文件，也没有漏项提示。
预期：指出 E02 缺少依据，定位到该输入框，并保留已经填写的内容。
请修正 evidence-panel.html，说明具体改动。
修正后检查：漏填时有提示，补齐后能导出，其他材料内容保持一致。
```

若工具直接改了文件，重新打开该文件；若返回新附件，下载修正版并核对文件名；若只返回修改后的完整代码，更新练习文件，保留之前的备份。刷新会清空本例的填写内容，复测时需要按相同输入重做。

这个过程说明修改为什么发生、改了哪一步、怎样知道改好。可以使用[问题求助卡](../08-练习册与案例库/02-可复制作品模板.md)记录自己的真实问题。不要把示例中的失败复制成自己的测试结果。

## 第六步：请别人试用，再决定是否继续

请一位可能使用这类工具的人完成“根据三条材料留下可追溯的核查记录”。先观察他如何操作；需要帮助时记录帮助发生在哪里。用[试用与修改记录卡](../08-练习册与案例库/02-可复制作品模板.md)分开写实际行为、对方解释和自己的推断。

若对方找不到下载入口，先修入口；若对方误以为面板已自动核查事实，先修用途说明。改完再试同一任务，检查原来的卡点是否消失。找不到试用者时，保留“待试用”，先完成个人验收即可。

## 怎样算完成，下一步学什么

你应能拿出任务说明、可打开的文件、与输入一致的导出记录，并解释一次修改的依据。若要把它带入真实工作，还需验证真实材料、使用习惯和维护责任；本次练习不证明这些条件已经满足。

这里用 AI 编程工具帮助制作页面，页面运行时本身没有用模型。在制作过程中，如果应用会写文件、检查页面、收到错误后继续修正，你体验到的是 Agent 的工具使用过程；组织工具调用、回传结果、记录进展的支撑属于 Harness 的职责。即使制作工具有这些能力，也要检查交付文件；单纯返回代码的对话不代表已经执行了完整检查。

可以用[工具地图](../06-工具地图与个人系统/01-按任务类型理解AI工具.md)认识这些基本操作，或通过[从 Prompt 到 Harness](../09-Agent与Harness工程/01-从Prompt到Harness工程.md)理解运行机制。以后给页面本身接入模型时，还需要处理输入发送、调用失败和结果核验。
