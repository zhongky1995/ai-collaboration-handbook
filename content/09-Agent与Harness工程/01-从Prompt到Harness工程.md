## 为什么长 Prompt 仍不是 Harness？

Harness 不是更长的 Prompt，而是模型与任务周围的运行控制系统；本库用目标、上下文、状态、工具、循环、权限、验证、可观测性八构件解释它。

### 在固定研究简报中操作

沿演化阶梯找出每层新增的控制和解决的失败，不能只背五个名词。

### 在「从 Prompt 到 Harness 工程」中最容易犯的错

把所有控制都写成自然语言，权限、状态、Trace 和失败恢复仍不可强制、不可观察。

### 「最小 Harness」应留下什么证据

- **结构检查**：能指出八构件在同一任务中的位置，并解释每层解决的失败。
- **固定案例对照**：说明这次修改解决了哪一种失败，并保存进「最小 Harness」。
- **需人工核验**：事实、业务适用性与高风险决定仍由人负责。

本页为主脊柱增加 **权限、预算、Trace、Eval、异常、成本与恢复**；满足以上证据后，回到作品继续推进 Skill / AgentOS：封装、交接、登记与迭代。

## 深入理解与原有知识

## 一句话结论

当 AI 只需要完成一次低风险生成时，Prompt 可能已经够用；当它要跨多轮读资料、调用工具、改变外部状态并持续推进时，决定可靠性的就不再是一段 Prompt，而是模型周围的整套运行系统。

本库把这套系统称为 **Harness**：它给模型准备目标、上下文、状态、工具、循环、权限、验证和运行记录，让一个概率性的模型能在可控边界内完成工作。

这是一项工作定义，不是唯一行业标准。不同框架会使用 runtime、orchestration、agent system 等名称，但它们都在解决相似问题：模型下一步看见什么、能做什么、做完如何判断、出错如何停下。

## 为什么“换更强模型”还不够

模型擅长根据当前信息生成下一步，但它不会天然拥有你的完整工作环境。一个看似简单的“每周生成竞品动态简报”，至少隐藏了这些问题：

- 去哪里找资料，哪些来源可信？
- 这周和上周的状态在哪里？
- 搜索结果太多时，哪些进入上下文？
- 看到价格变化后，是只记录，还是发消息？
- 来源冲突时继续推断，还是停下来问人？
- 怎样证明它真的查过资料，而不是写了一份像真的报告？
- 下周如何复用这次失败经验？

这些问题大多不属于“模型会不会写”，而属于系统如何提供环境和约束。

本手册采用一个统一判断：模型只是运行时的一部分，它的行为由提示词、工具描述和上下文共同塑造；Agent Loop、权限、上下文压缩和验证必须在同一个运行循环里协同。**Agent 能力不是模型的单点能力，而是模型与外部系统的组合能力。**

## 五个层级解决不同问题

| 层级 | 主要解决什么 | 适合例子 | 不能替代什么 |
|---|---|---|---|
| Prompt | 这一次要做什么 | 改写一封邮件 | 不能稳定管理多步骤和状态 |
| Prompt Template | 同类任务的输入结构 | 每周会议纪要模板 | 不能决定复杂步骤如何推进 |
| Workflow | 固定路径和检查点 | 事实整理 → 推断 → 简报 → 验收 | 不擅长路径随环境变化的任务 |
| Agent | 根据观察选择下一步 | 发现新信息后决定继续搜索或汇总 | 不能自动保证安全和可靠 |
| Harness | 让 Agent 在边界内运行、验证和恢复 | 工具、权限、状态、日志、Eval 的组合 | 不能消除模型不确定性，只能管理它 |

升级不是越高越好。路径明确的任务用 Workflow 更便宜、更透明；只有任务需要根据环境反馈反复选择动作时，Agent 才带来真实价值；只有 Agent 的错误会产生实际成本时，Harness 的控制才必须显式设计。

## Harness 的八个构件

内部标准使用八构件模型检查一个 Agent 系统是否完整：

```text
目标与指令 ─┐
上下文 ─────┤
状态 ───────┤
工具 ───────┼─> Agent Loop ─> 产物 / 外部变化
权限 ───────┤        │
验证 ───────┤        v
可观测性 ───┘    继续 / 停止 / 恢复 / 交给人
```

| 构件 | 必须回答的问题 | 缺失后的典型失败 |
|---|---|---|
| 目标与指令 | 成功是什么，不做什么？ | 看起来很勤奋，却一直偏离目标 |
| 上下文 | 这一轮必须知道什么，什么可以不带？ | 被旧信息和工具噪声淹没 |
| 状态 | 已完成什么、当前在哪、还缺什么？ | 重复劳动、跳步、跨会话失忆 |
| 工具 | 能读取、计算、写入或连接什么？ | 只能“说”，不能核验和行动 |
| 循环 | 如何根据结果决定下一步？ | 把单次生成误叫成 Agent，或无限循环 |
| 权限 | 哪些动作自动做，哪些必须确认？ | 一次错误判断直接变成外部损失 |
| 验证 | 如何知道结果和过程合格？ | 模型自己宣布完成，没有证据 |
| 可观测性 | 发生了什么，失败在哪一步？ | 只能看到坏结果，无法定位和复现 |

其中任何一项都不能只靠一句“请认真一点”替代。Prompt 是软约束：它能影响模型，但可能在长上下文中被稀释。工具校验、权限拦截、输出 Schema 和测试是硬约束：不符合条件就不能继续。可靠系统通常把软约束和硬约束叠加，而不是二选一。

## 一个业务案例：竞品动态简报

先看只有 Prompt 的版本：

```text
请搜索本周竞品动态，生成一份简报，并给出建议。
```

它把范围、来源、时间、判断、发布和核查全交给模型猜。

最小 Harness 版本可以这样拆：

| 构件 | 设计 |
|---|---|
| 目标 | 找出指定 5 个竞品在最近 7 天的可验证变化；不做市场份额预测 |
| 上下文 | 竞品名单、上周快照、认可来源清单、简报格式 |
| 状态 | `待检索 → 已取证 → 待比对 → 待人工确认 → 已发布` |
| 工具 | 只读网页、读取上周文件、写入本周草稿；不能直接群发 |
| 循环 | 每个竞品检索 → 保存来源 → 与上周比对 → 判断是否继续补证 |
| 权限 | 写本地草稿可自动；对外发送和改竞品名单必须确认 |
| 验证 | 每条变化有日期和来源；建议必须绑定已确认变化 |
| 可观测性 | 记录来源、抓取时间、未访问页面、冲突和人工修改 |

这个系统仍可能漏信息，但失败会更早暴露：找不到来源时进入“待补证”，来源冲突时进入“待人工确认”，而不是继续生成一段自信结论。

## 四道门：任务值得 Agent 化吗

在设计 Harness 之前，先过四道门：

1. **路径不确定性**：任务是否真的需要根据中间结果选择下一步？如果步骤始终固定，用 Workflow。
2. **环境反馈**：AI 是否需要读取工具结果或外部状态？如果不需要，多轮生成未必是 Agent。
3. **可验证性**：能否定义完成、失败和停止？如果只能凭“感觉不错”，先不要自动化。
4. **风险可控性**：错误能否被限制、回退或交给人？如果一次错误不可逆，先缩小工具权限。

只有四道门都能回答，才值得继续设计 Agent。复杂并不是 Agent 化的理由；**需要自主选择，而且这种自主能被验证和约束**，才是理由。

## 三个反模式

### 反模式一：用超长 Prompt 冒充系统

把所有规则、历史、工具说明和例子塞进一条 Prompt，短期可能有效，长期会出现冲突、过期和注意力稀释。应该把稳定规则、动态状态、外部资料和工具结果分开管理。

### 反模式二：先给全部权限，再补安全规则

“让它先跑起来”不等于允许它发送消息、删除文件或修改系统。最小闭环可以先在只读资料和草稿目录里跑通，再逐步扩大权限。

### 反模式三：只验收最后一份漂亮报告

最终文案可能正确，但来源错误；也可能结论正确，只是偶然猜中。Agent 系统需要同时验收结果和关键轨迹：读了什么、调用了什么、为什么停下、哪里需要人确认。

## 验收标准

完成这一讲后，你应该能：

- 用一句话区分模型、Agent 和 Harness。
- 解释为什么更强模型不能替代状态、权限和验证。
- 用八构件检查一项复杂 AI 任务。
- 用四道门判断它是否值得 Agent 化。
- 指出至少一个应该由硬约束而不是 Prompt 承担的规则。
