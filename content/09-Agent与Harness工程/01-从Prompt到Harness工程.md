# 进入 Agent 之前：从 Prompt 到 Harness

你让 AI 整理一份资料，它可能只返回一段文字，也可能读取几个文件、补查缺失信息、保存结果，再检查文件能否打开。后一种过程需要把多次判断和实际操作组织起来。

这一篇先解释这个过程中的 Agent、工具和 Harness。即使暂时不开发系统，也可以用这些概念理解手里的 AI 应用正在做什么。后续进阶课再展开具体工程设计。

## 先看一个会不断重复的任务

假设团队每周都要整理一份竞品更新简报。

一次性完成它并不难：给 AI 几份网页和公告，让它提取变化、比较差异、起草摘要，再由人核验。

真正进入持续运行后，新的问题出现了：

- 某个网页打不开，要重试、换来源，还是停止？
- 两个来源说法冲突，应该采用哪一个？
- 系统能读取哪些目录，能不能访问外部网站？
- 简报可以自动保存，但能不能自动发送？
- 中途失败后，是从头再来，还是从已经核验的材料继续？
- 如果结果有问题，谁能查到它使用过什么材料、采取过什么动作？

这些问题已经不是一句 Prompt 能回答的。它们关心的是系统怎样运行。

## 协作方法与运行支撑分别解决什么

| 层次 | 主要解决的问题 | 什么时候够用 |
|---|---|---|
| Prompt | 这一次怎样生成一个候选 | 单轮、低风险、有人立即检查 |
| 模板 | 同类请求怎样复用相同字段 | 输入输出稳定，但仍由人逐次发起 |
| Workflow | 多步任务怎样按预先定义的步骤与分支推进 | 正常路径和主要异常路径可以事先写清 |
| Agent | 中间结果不同时，系统怎样在边界内选择下一步 | 需要动态选择工具、来源或重试方式 |
| Harness | 怎样组织模型调用、工具执行和结果回传，并管理运行过程 | 需要上下文、状态、权限、记录、验证和恢复等支撑 |

Prompt、模板与 Workflow 可以在 Agent 应用中继续使用。Harness 则是运行支撑，不是学完 Agent 后必须升级购买的另一个产品。现成应用通常已经封装了一部分运行能力；具体有哪些，要看产品和配置。

## 用一次文件任务理解模型、工具和 Harness

本课把 **Agent** 理解为围绕目标、根据当前状态和环境反馈选择后续动作的系统。模型提供理解、生成和选择能力；工具执行具体动作；**Harness** 可以先理解为“让模型能够连续使用工具完成工作的运行支撑”。

不同项目对 Harness 的范围划分并不完全相同。本课采用较宽的教学口径：它组织运行循环，以及循环所需的上下文、状态、工具接口和控制机制。实际产品往往把这些能力封装在一起，用户不一定看到一个叫“Harness”的设置。

假设任务是“读取会议记录，生成一份纪要文件”。下面是**教学运行示意**，工具名称仅表示动作，不是某个产品的固定接口。

### 1. 准备：这一轮从什么信息开始

Harness 把任务要求、可用工具和相关状态交给模型。模型根据目标判断需要哪些材料；必要时提出列出工作目录中的文件，再由对应工具执行。

用户可能看到材料列表或读取计划。这说明系统在确定工作对象，还没有生成纪要。

### 2. 读取：把动作变成实际结果

模型指定要读取的会议记录。Harness 按当前规则检查调用范围，组织工具执行；读取工具返回正文或错误，Harness 再把这个结果交给后续模型调用。

用户可能看到“已读取”或“找不到文件”。模型只有取得正文，才有条件根据原文整理；读取失败时，需要先处理文件位置或可访问性。

### 3. 整理：根据返回的信息选择后续动作

模型基于正文生成纪要草稿。信息不足时，它可能提出补读其他材料，也可能标记未知。Harness 更新本轮可见材料与任务进展，组织需要执行的补充读取。

用户可能看到初稿或明确的待确认项。补读之后的结果应影响下一轮判断，而不只是重复同一段回答。

### 4. 保存：从文字变成一个文件

模型给出纪要内容与目标位置。写入工具实际创建或更新文件；Harness 记录写入结果，并把成功或失败交回后续步骤。

用户可能得到文件链接、工作目录中的文件，或写入失败提示。具体位置取决于本地或云端运行环境。

### 5. 检查：决定继续修订还是结束

读取工具重新打开文件；具备相应能力时，其他工具检查格式或内容结构。模型按任务标准比较纪要与原文，Harness 组织检查结果回传，并按配置继续修订、结束或等待处理。

用户应看到交付文件、检查情况和未完成事项。应用是否实际执行这些检查，需要从当前任务记录确认。

模型说“准备保存”是一个意图；写入工具返回结果，才提供了文件是否写入的证据；重新打开和对照检查，才能进一步判断交付是否正确。文件确实存在，也不代表里面的判断全部可靠。

## Harness 怎样帮助任务继续推进

当你手动协作时，通常需要自己复制材料、把上一步结果贴回去、记住进度、保存版本，再检查结果。Harness 把其中一部分工作组织成运行机制，让模型有条件持续处理任务。

**准备上下文：让每一轮拿到相关材料。** 按需读取长文件，选择本轮需要的信息，减少反复粘贴全部历史的工作。

**衔接动作：让工具结果参与下一轮。** 读到文件后继续整理，读不到时处理错误；每一步依据实际返回继续。

**记录进度：让已经完成的工作可查。** 保存任务状态、中间文件和进度记录，帮助用户或后续步骤找到已完成部分与剩余问题。

**恢复工作：让中断后有条件继续。** 在支持恢复的环境中，加载已有状态与产物，并检查原文件等环境是否变化，再处理未完成部分。

**检查交付：让结束有可说明的依据。** 按配置执行检查、记录结果，失败时继续修订或说明阻碍，完成时返回作品与检查情况。

**管理范围：让执行符合本次任务的条件。** 检查工具范围、权限、轮次或时间预算；达到限制时停止、等待或交给人处理。

这些是运行支撑可以承担的职责，不是所有工具都完整具备的功能，也不保证任务一定成功。尤其要区分：保留聊天记录、保存工作进度、能够可靠恢复，是三个不同的能力。

Harness 也不等于一段更长的提示词。写“请记住进度”表达了要求；要在中断后继续工作，还需要实际保存状态、重新加载状态，并检查原文件是否发生变化。写“只改这个目录”是指令；要强制限制范围，还需要工具或运行环境落实检查。

上述运行循环可参照 [Claude Agent SDK 的工程说明](https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk)。进度文件、分步推进与检查的具体实践见 [Anthropic 长任务 Harness 文章](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。本页表格与会议例子是教学综合，不是统一行业架构。

## 回到每周竞品简报

如果材料每周都由人整理好，系统只按固定顺序提取、比较、起草和等待确认，一条 Workflow 可能已经足够。

只有出现下面这类动态选择，Agent 才开始有价值：

- 来源不可用时，在授权列表里选择备用来源；
- 发现版本冲突时，进入核查分支；
- 信息不足时，决定补充检索还是标记未知；
- 检查未通过时，只重做有问题的部分。

即使引入 Agent，也不意味着它可以自行发布。Harness 仍应限制：

- 只能读取授权材料；
- 外部检索和敏感数据按规则处理；
- 重试次数有上限；
- 每次来源选择和修改都有记录；
- 对外发送前必须由负责人确认。

使用者最终应能看到简报、主要来源、未决问题和执行结果。后续是否扩大自动化范围，要依据实际任务记录与检查结果判断。

## 作为使用者，先做一个小观察

打开支持文件任务的 Agent 应用，选一份可以练习的材料，明确要求“只整理成草稿文件，保留原文件，并说明保存位置和未完成事项”。需要认识产品与常见工具能力时，先看[按任务类型理解 AI 工具](../06-工具地图与个人系统/01-按任务类型理解AI工具.md)。

运行时留意三件事：它是否实际读取了材料，是否产生了文件或明确交付，是否报告了检查和未完成事项。若只收到计划，可进一步要求执行已明确的文件任务；若文件不存在，先定位保存失败；若事实有问题，回到材料和判断标准修订。

这一观察能帮助你找到需要补强的环节。只看应用的一次表现，无法反推出它完整的内部架构。

## 进入进阶层前，先过三个判断

### 1. 任务已经稳定吗

输入、输出和验收方式仍在频繁变化时，先继续打磨任务和 Workflow。否则系统会把变化中的试验误当成固定规则。

### 2. 动态选择真的必要吗

如果所有任务都走同一条路径，Workflow 更简单、更容易检查。不要为了使用 Agent 而制造分支。

### 3. 运行责任有人承担吗

至少要有人决定工具权限、敏感数据边界、人工确认点和故障处理方式。没有负责人，就不应让系统扩大行动范围。

三个判断都比较清楚，才适合继续学习：系统怎样根据当前情况选择下一步，怎样调用工具，怎样限制权限，以及怎样记录、检查和恢复运行过程。后续各讲会分别解释这些概念。

## 这一层不承诺什么

进阶工程课不会提供一个“全自动员工”的万能配方。它关注的是更朴素的问题：

> 当 AI 不再只生成一段文字，而是开始读取状态、调用工具并采取动作时，怎样让过程仍然可见、可控、可停止、可恢复。

这也是 Harness 存在的原因。
