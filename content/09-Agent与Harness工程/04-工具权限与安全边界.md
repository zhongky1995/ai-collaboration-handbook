# 工具权限与安全边界

<!-- PRACTICE:START -->
> **S5 · Harness · 当前作品：最小 Harness**

## 权限矩阵怎样从提醒变成执行边界？

权限要按对象×动作设计 allow/ask/deny，并结合沙箱、路径范围、敏感日志和失败关闭；提示词提醒不能替代执行层限制。

### 在固定研究简报中操作

把不可逆的发送设为 ask，把敏感材料外发设为 deny，再写授权升级需要谁批准。

### 在「工具权限与安全边界」中最容易犯的错

全 allow 违反最小授权；全 ask 造成确认疲劳；敏感数据写入日志又扩大泄漏面。

### 「最小 Harness」应留下什么证据

- **结构检查**：对象×动作均有理由，敏感外发 deny，不可逆动作 ask，日志最小化。
- **固定案例对照**：说明这次修改解决了哪一种失败，并保存进「最小 Harness」。
- **需人工核验**：事实、业务适用性与高风险决定仍由人负责。

本页为主脊柱增加 **权限、预算、Trace、Eval、异常、成本与恢复**；满足以上证据后，回到作品继续推进 Skill / AgentOS：封装、交接、登记与迭代。

## 深入理解与原有知识

## 一句话结论

模型提出动作，不等于系统应该执行动作。可靠 Harness 必须在工具层再次检查范围、参数、权限和风险：低风险动作可自动，高风险动作要确认，明确禁止的动作即使模型反复请求也不能放行。

Prompt 中的“请小心”是软约束；工具校验、审批、沙箱和拒绝规则是硬约束。两者要叠加。

## 工具把语言错误变成现实错误

没有工具时，模型答错通常只产生一段错误文字。有了工具后，它可能：

- 读取文件、数据库和网页。
- 写入文档、表格和代码。
- 发送邮件、消息或社交内容。
- 提交表单、下单、付款或删除数据。

Agent 的价值来自这些真实动作，风险也来自这里。安全设计不能只检查最终回答，还要在动作发生前决定“允许、询问还是拒绝”。

## 权限之前，先把工具写成可执行契约

工具描述不只是给人看的功能介绍，它是 Agent 理解动作空间的接口。一个工具如果名字含糊、参数全是自由文本、成功与失败返回相同格式，再强的模型也会稳定地产生误用。

一份最小工具契约要回答：

| 契约项 | 必须说清什么 | 缺失后的典型失败 |
|---|---|---|
| 意图 | 这个工具完成哪一种动作，不负责什么 | 用相邻工具勉强完成任务 |
| 前置条件 | 调用前必须已有哪种状态、材料或授权 | 输入不完整仍强行执行 |
| 输入 | 必填字段、类型、枚举、范围和示例 | 参数猜测、单位混用、路径越界 |
| 输出 | 成功、失败、等待、状态未知分别怎样表示 | 把“已提交”误当“已完成” |
| 副作用 | 会读取、写入、发送、覆盖或收费吗 | 低估真实影响 |
| 重复语义 | 超时重试会复用结果，还是再次产生动作 | 重复发信、重复扣款、重复创建 |
| 恢复 | 失败后能查询、撤销、补偿还是只能交给人 | 盲目重试扩大损失 |

尽量用结构化字段和有限选项表达关键参数。例如，把一个模糊的 `message_action` 拆成 `draft`、`preview`、`send`，并让 `send` 必须携带已批准预览的版本标识。这样，工具接口本身就在阻止“批准的是 A，执行时变成 B”。

设计工具时采用一个简单原则：**让正确动作容易表达，让危险或含糊动作无法在不显式声明的情况下发生。** 权限矩阵负责决定能否执行，工具契约负责保证系统知道自己准备执行什么；两者不能互相替代。

## 先按影响分四级

| 级别 | 动作特征 | 例子 | 默认策略 |
|---|---|---|---|
| L0 只读 | 不改变外部状态 | 搜索、读取指定文件、计算 | 可自动，但仍限制来源和范围 |
| L1 可逆写入 | 改动可在受控范围内恢复 | 写草稿、更新临时表、创建新文件 | 在沙箱或指定目录自动，保留版本 |
| L2 外部行动 | 会影响他人或正式系统 | 发邮件、提交后台、发布内容 | 动作前人工确认，展示最终参数 |
| L3 高风险/难逆 | 可能造成财务、合规、数据或声誉损失 | 删除、付款、签约、生产配置 | 默认禁止或双人授权 |

风险不只由工具名称决定。同一个“写文件”工具，写临时草稿和覆盖正式合同是不同级别；同一个浏览器，查看网页和点击“发布”也不同。

## 用 allow / ask / deny 写权限矩阵

权限应该具体到“工具 + 动作 + 范围”，而不是笼统地说“可以用浏览器”。

| 工具动作 | 范围 | 决策 | 原因 |
|---|---|---|---|
| 读取网页 | 公开来源清单 | allow | 只读、范围明确 |
| 读取文件 | 当前项目资料目录 | allow | 完成任务所需 |
| 写文件 | `drafts/` 新文件 | allow | 可逆且不覆盖正式产物 |
| 覆盖文件 | `final/` | ask | 可能覆盖已批准版本 |
| 发送邮件 | 任意收件人 | ask | 影响外部人员 |
| 上传原始客户资料 | 外部服务 | deny | 违反数据边界 |
| 删除目录 | 任意 | deny | 超出任务需要且难恢复 |

权限矩阵还要说明授权是否可以扩展：允许“把草稿写到 `drafts/`”不等于允许覆盖 `final/`，允许发送给测试邮箱不等于允许群发客户。

## 五层防线

### 1. 指令层：告诉模型正确行为

写清适用范围、禁止动作和人工确认点，让模型大多数时候提出合理动作。

### 2. 工具 Schema：让错误参数难以出现

把自由文本变成结构化字段，例如：

```text
action: draft | preview | publish
audience: internal | customer | public
requires_approval: true | false
```

Schema 能减少歧义，但不能证明参数安全。

### 3. 权限层：独立判断 allow / ask / deny

权限检查不能依赖模型自己声明“这是安全的”。系统根据工具、范围、目标和当前授权再次判断。

### 4. 执行环境：限制实际影响

- 用沙箱或专用工作区隔离写入。
- 只挂载任务所需目录。
- 凭证按任务和时限发放。
- 先生成预览，再执行外部动作。
- 为可逆写入保留版本或回滚点。

### 5. 事后证据：记录和验证

保存动作、参数、授权人、时间、工具结果和影响范围。事后日志不能替代事前拦截，但能支持复盘和追责。

内部权限标准采用纵深防御：模式开关、细粒度规则、路径验证、运行隔离和事后证据共同工作。任何单层都可能失效，所以关键边界必须有第二道、第三道控制。

## Fail closed：不确定时不要猜着执行

以下情况应停止，而不是“尽量完成”：

- 权限规则互相冲突。
- 目标路径含变量、通配符或无法解析的跳转。
- 工具返回模糊状态，不知道动作是否成功。
- 预览内容和即将提交的内容不是同一版本。
- 授权针对 A，但执行参数变成 B。
- 请求需要新的凭证或更大范围。

Fail closed 的含义是：没有明确证据证明允许，就不执行高影响动作。系统可以降级为草稿、计划或待审批，而不是完全失败。

## 人在回路不等于每一步都弹窗

过度询问会让人习惯性点击“允许”，反而降低安全性。人工门应放在真正需要承担责任的节点：

| 节点 | 人要判断什么 |
|---|---|
| 目标变更 | 是否允许扩大任务范围 |
| 来源冲突 | 哪条依据可以采用 |
| 正式写入 | 是否覆盖当前权威版本 |
| 外部发送 | 收件人、正文、附件是否正确 |
| 高风险例外 | 是否接受超出默认规则的风险 |

确认界面应展示即将发生的具体动作，而不是只问“是否允许工具运行”。

## 案例：社交内容发布 Agent

目标：根据已批准的内容计划生成并发布社交卡片。

### 不安全设计

- 浏览器拥有全部账号权限。
- AI 可自己选择素材和文案。
- 生成完成后直接发布。
- 日志只记“发布成功”。

### 分级设计

| 阶段 | 自动能力 | 控制 |
|---|---|---|
| 读取计划 | 读已批准选题和品牌资料 | 只读指定目录 |
| 生成草稿 | 写图片和文案到任务目录 | 禁止覆盖模板源文件 |
| 质量检查 | 检查尺寸、可读性、来源和敏感词 | 失败则回到草稿，不可绕过 |
| 发布预览 | 展示账号、平台、正文、图片和时间 | 生成不可编辑的确认快照 |
| 正式发布 | 调用平台动作 | 必须由人批准当前快照 |
| 发布后 | 保存平台返回 ID 和页面链接 | 无返回 ID 视为状态未知，停止重试 |

如果网络超时，系统不能直接再次发布，因为第一次可能已经成功。它应先用平台 ID 或页面查询确认状态，再决定是否重试。这是“世界状态”和权限共同作用的例子。

## 敏感日志也需要权限

可观测性可能记录模型输入、工具参数和输出，其中包含客户资料、凭证或个人信息。设计日志时要明确：

- 哪些字段不记录。
- 哪些字段脱敏或哈希。
- 谁能查看。
- 保留多久。
- 导出和分享前如何再检查。

“为了调试全部记录”不是安全默认值。

## 练习：制作工具权限矩阵

选一个会使用 3 种以上工具的任务，填写：

| 工具/动作 | 输入与输出状态 | 允许范围 | allow / ask / deny | 硬校验 | 回退方式 | 记录字段 |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |

然后加入三个异常：

1. 路径超出任务目录。
2. 外部动作超时，成功状态未知。
3. 人批准后，参数发生变化。

为每种异常写出唯一处理：拒绝、重新确认、查询状态、回滚或交给人。

## 验收标准

完成这一讲后，你应该能：

- 按真实影响而不是工具名称给动作分级。
- 为一个工具写清意图、前置条件、输入、输出、副作用和重复语义。
- 写出包含范围的 allow / ask / deny 权限矩阵。
- 区分 Prompt 软约束和工具硬约束。
- 为高影响动作设计预览、确认和事后证据。
- 解释 Fail closed、最小权限和沙箱分别解决什么问题。
- 说明日志本身为什么也需要数据边界。
