# Agent Loop 与状态推进

<!-- PRACTICE:START -->
> **S4 · Agent Loop · 当前作品：Agent 运行卡**

## Agent 每一轮怎样证明自己在推进？

Agent Loop 每轮必须产生可观察状态变化：观察、选择行动、接收工具结果、更新状态、继续/等待/失败/停止。

### 在固定研究简报中操作

给三次重试设置不同策略和上限；如果工具结果没有写回状态，这一轮不算有效推进。

### 在「Agent Loop 与状态推进」中最容易犯的错

重复同一行动、工具结果不写回状态、没有停止原因，都会形成看似忙碌的死循环。

### 「Agent 运行卡」应留下什么证据

- **结构检查**：Trace 中每轮都有状态变化，并能在上限或等待人工时正确停止。
- **固定案例对照**：说明这次修改解决了哪一种失败，并保存进「Agent 运行卡」。
- **需人工核验**：事实、业务适用性与高风险决定仍由人负责。

本页为主脊柱增加 **观察、动作、工具结果、状态更新、停止与恢复**；满足以上证据后，回到作品继续推进 Harness：控制权限、预算、Trace 与 Eval。

## 深入理解与原有知识

## 一句话结论

Agent Loop 不是“让模型多回答几轮”，而是一个持续更新状态的控制循环：准备上下文，调用模型，选择动作，检查权限，执行工具，接收结果，更新状态，再判断继续、停止、恢复还是交给人。

如果没有状态、工具结果和停止条件，多轮对话只是长聊天，不是可靠的 Agent 运行。

## 一轮 Agent 到底发生什么

可以把通用循环拆成八步：

```text
1. 读取目标和当前状态
2. 选择这一轮需要的上下文
3. 让模型提出下一步或最终结果
4. 校验动作格式、范围和权限
5. 执行工具或生成中间产物
6. 把观察结果写回状态
7. 运行质量检查和风险检查
8. 继续 / 完成 / 重试 / 降级 / 交给人
```

内部标准把 Agent Loop 视为 Agent 系统的运行锚点，因为工具调用、上下文压缩、权限判断和失败恢复最终都在循环中发生。无论采用什么框架，都要遵守同一机制：**每一轮都会让模型看到的世界和系统状态发生变化。**

## Agent Loop 和普通 Workflow 的差别

| 维度 | Workflow | Agent Loop |
|---|---|---|
| 下一步 | 通常由人预先写好 | 根据当前观察动态选择 |
| 路径 | 相对固定 | 可能分支、回退、补查 |
| 状态 | 主要记录进行到第几步 | 还记录环境、证据、预算和风险 |
| 工具 | 在指定步骤调用 | 模型可根据需要提出调用 |
| 结束 | 完成最后一步 | 满足完成条件、达到限制或被阻止 |
| 风险 | 错误沿固定链传播 | 错误可能在自主循环中被放大 |

如果任务只是“依次完成 A、B、C，再让人确认”，Workflow 更透明。Agent 的价值在于 A 的结果会决定是做 B、C，还是回到 A 补信息。

## 状态不是聊天记录

聊天记录包含大量过程，但状态应该只保存接下来做决定需要的有效信息。本库把状态分成五类：

| 状态类型 | 记录什么 | 例子 |
|---|---|---|
| 任务状态 | 目标、范围、当前阶段、完成项 | 已完成 3/5 个竞品核查 |
| 世界状态 | 外部环境当前是什么样 | 页面更新时间、文件版本、待处理消息 |
| 证据状态 | 已确认事实、来源、冲突、缺口 | 价格变化有两条来源，但日期冲突 |
| 资源状态 | 剩余时间、轮次、Token、调用额度 | 还允许两轮补查 |
| 控制状态 | 权限、人工门、重试和停止原因 | 对外发送待批准；已重试一次 |

把状态和对话历史分开有两个好处：压缩历史时不容易丢失关键进度；换人或换 Agent 时可以用状态包快速接续。

一个最小状态记录可以是：

```text
任务：核查本周 5 个竞品变化
当前阶段：补证
已完成：A、B、C
当前证据：D 有一条官网来源，一条媒体来源
冲突：两条发布日期不同
待办：确认 D；检查 E
权限：只读检索和写草稿
预算：剩余 2 轮
需要人判断：若 D 无法确认，是否在简报中标“未证实”
```

## 继续和停止都要有理由

一个可靠循环不只有“继续”和“完成”。至少要区分：

### 可以继续

- 工具返回新信息，且任务仍未完成。
- 发现证据缺口，预算内还有明确补查路径。
- 验证失败，但失败原因可修复。
- 人工确认已经返回，可以进入下一阶段。

### 应该正常完成

- 交付物齐全。
- 通过标准已满足。
- 没有未披露的高风险缺口。
- 状态、来源和产物位置已经记录。

### 应该停止并交给人

- 来源冲突会影响核心结论。
- 需要超出原范围或权限的动作。
- 涉及对外发布、客户承诺或不可逆操作。
- 连续失败达到上限。
- 目标本身发生变化，原状态不能直接沿用。

### 应该失败关闭

- 工具结果不可解析，无法证明动作是否成功。
- 权限状态不明确。
- 必要输入缺失且没有可信默认值。
- 系统无法判断自己看到的是完整内容还是截断预览。

“失败关闭”不是崩溃，而是宁可明确停下，也不在不确定边界上假装完成。

## 同步循环与异步续跑不是一回事

有些任务的下一条观察马上就能得到，例如读完文件后立刻进入下一轮；另一些任务必须等人审批、等定时器、等外部系统回调或等新消息。后者不能让 Agent 一直占着循环空转，而应把任务保存为“等待中”，等事件到来后再从状态继续。

| 运行方式 | 下一步从哪里来 | 关键控制 |
|---|---|---|
| 同步循环 | 当前工具立即返回结果 | 轮次上限、结果写回、停止条件 |
| 异步续跑 | 人工回复、定时触发、外部回调或新消息 | 持久化状态、事件去重、过期处理、恢复检查 |

异步事件至少要让系统知道：它属于哪个任务、来自哪里、何时发生、携带什么结果、是否已经处理过。事件到来只代表“可以重新判断”，不代表自动获得更大权限。

例如发送审批结果时，Agent 应先检查：原草稿版本是否仍然相同、批准对象是否与当前参数一致、任务是否已经被取消。若同一回调重复到达，系统应识别为同一个事件，避免重复发布或重复写入。这种“重复执行仍不产生额外副作用”的性质称为**幂等**。

最小异步状态可以写成：

```text
任务 ID：
当前状态：waiting / resumed / cancelled / expired
等待事件：谁在什么条件下返回什么
关联版本：草稿、参数或外部对象的版本
事件去重标识：
超时后动作：提醒 / 降级 / 交给人
恢复前检查：权限、版本、目标是否仍有效
```

这样，Agent Loop 才能从“在一次对话里连续调用工具”，扩展成“跨时间接收事件、恢复任务并保持责任边界”的运行系统。

## 恢复不是无限重试

Agent 常见的恢复方式包括：

| 失败 | 合理恢复 | 不合理行为 |
|---|---|---|
| 临时网络错误 | 有上限地重试，记录次数 | 一直重试直到耗尽额度 |
| 上下文过长 | 压缩历史，恢复关键文件和状态 | 静默删除旧信息继续做 |
| 工具输出过大 | 保存完整结果，只带摘要和位置 | 把全部内容反复塞回上下文 |
| 输出格式错误 | 按 Schema 修复一次 | 每轮换一种格式继续猜 |
| 权限不足 | 请求授权或降级为草稿 | 绕过权限换别的工具完成 |
| 目标不清 | 停止并请人澄清 | 自行扩展目标 |

每种自动恢复都应有熔断条件：最大重试次数、最大轮次、最大成本或截止时间。连续失败通常意味着系统性问题，不是“再努力一次”能解决。

## 案例：资料研究 Agent 如何推进

目标：为一次内部决策查清某项政策是否已经生效。

### 第 1 轮

- 上下文：研究问题、地区、时间范围、认可来源。
- 动作：搜索官方发布渠道。
- 观察：找到征求意见稿，没有生效日期。
- 状态：`证据不足；不得写“已生效”`。
- 下一步：搜索正式文件和主管部门解释。

### 第 2 轮

- 动作：读取正式文件页面。
- 观察：找到文件编号和实施日期，但附件无法打开。
- 状态：核心事实有一手来源，细则缺失。
- 下一步：补查附件或权威解读；不扩大到媒体评论。

### 第 3 轮

- 观察：附件仍失败，预算达到上限。
- 验证：能确认“生效”和日期，不能确认某项具体例外。
- 终止：生成“已确认 / 未确认 / 不应推断”三栏简报，例外问题交给人继续。

这个 Agent 没有“把所有信息都查完”，但它在正确边界停止，并清楚说明证据缺口。可靠性来自状态和终止纪律，而不是写得更像专家。

## 可观测不等于暴露隐藏推理

为了复盘，不需要也不应要求保存模型的隐藏思维链。系统真正需要记录的是可验证事件：

- 输入了哪些任务字段和来源。
- 模型提出了哪个工具动作。
- 权限如何判定。
- 工具返回了什么可见结果。
- 状态字段如何变化。
- 哪个检查通过或失败。
- 为什么以“完成、受阻、超限或人工升级”结束。

这些事件足以定位大多数工程失败，同时比保存冗长自由推理更可控。

再用一个异常样例演练：工具返回空结果时，系统会继续、重试、降级还是停止？答案必须唯一且可解释。

最后增加一次异步演练：任务等待审批时，同一个“已批准”事件到达两次，而且草稿已经变更。说明系统应忽略什么、重新确认什么，以及恢复后进入哪个状态。

## 验收标准

完成这一讲后，你应该能：

- 区分固定 Workflow 和动态 Agent Loop。
- 把聊天历史与任务状态分开。
- 为一项任务写出至少三种终止原因。
- 为自动恢复设置上限和降级路径。
- 为等待中的任务写出事件去重、版本复核和过期处理。
- 说明哪些运行事件需要记录，且不依赖隐藏思维链。
