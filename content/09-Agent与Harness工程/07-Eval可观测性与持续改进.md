## Trace 和 Eval 各自回答什么？

Trace 回答发生了什么，Eval 判断是否达标；结果级与轨迹级证据必须一起看，失败分类才知道改 Prompt、Context、Workflow、权限还是模型。

### 在固定研究简报中操作

用一条失败 Trace 标注失控轮次、失败类型、修复项与回归样例，再决定是否提升版本。

### 在「Eval、可观测性与持续改进」中最容易犯的错

只有 Trace 没有判据只能看热闹；只有总分没有轨迹又无法定位越权或失控轮次。

### 「最小 Harness」应留下什么证据

- **结构检查**：一条失败能定位轮次、分类原因、指定修复，并通过回归样例验证。
- **固定案例对照**：说明这次修改解决了哪一种失败，并保存进「最小 Harness」。
- **需人工核验**：事实、业务适用性与高风险决定仍由人负责。

本页为主脊柱增加 **权限、预算、Trace、Eval、异常、成本与恢复**；满足以上证据后，回到作品继续推进 Skill / AgentOS：封装、交接、登记与迭代。

## 深入理解与原有知识

## 一句话结论

Eval 回答“这套方法在代表性样例上是否可靠”，可观测性回答“这一次运行发生了什么、失败在哪一步”。两者结合，才能把坏结果转成可定位的系统改进，而不是每次都重新调 Prompt。

Agent 不只要验收最终答案，还要验收关键轨迹：是否选对工具、使用了正确来源、遵守权限、正确交接，并在该停止时停止。

## 三层质量不能混成一个分数

| 层级 | 要回答的问题 | 例子 |
|---|---|---|
| 输出质量 | 最终产物对不对、能不能用？ | 简报事实准确、结构完整 |
| 过程质量 | 它是如何得到结果的？ | 调用了认可来源，未越权，正确处理冲突 |
| 业务结果 | 这项能力是否改善了真实工作？ | 减少遗漏、缩短交接、降低人工返工 |

输出好不代表过程可靠：模型可能偶然猜对。过程合规也不代表业务有价值：系统可能稳定地产出没人使用的报告。三层需要分别定义证据。

入门课程的轻量 Eval 已经覆盖输出评分。本讲增加的是 Agent 运行层。

## Trace 是端到端运行记录

内部可观测性标准把一次完整工作流记为 Trace，把其中的模型生成、工具调用、handoff、guardrail 和状态变化记为可检查事件：

```text
Trace：一次“生成竞品周报”的完整运行
├─ 任务准备
├─ 模型轮次 1
│  ├─ 工具调用：搜索官网
│  └─ 状态更新：找到 2 条变化
├─ 模型轮次 2
│  ├─ 工具调用：读取来源
│  └─ 权限检查：只读通过
├─ Handoff：交给核查单元
├─ Guardrail：阻止无来源建议
└─ 终止：needs-decision
```

一次 trace 至少应该能回答：

- 运行属于哪个任务和版本。
- 使用了哪个能力包和 Eval 规则。
- 每个外部动作的输入、结果和权限判定。
- 状态在何时发生关键变化。
- 哪个检查失败，采取了什么恢复。
- 最终以什么原因结束。

不需要保存模型的隐藏思维链。可见输入、工具动作、结构化状态、检查结果和简短决策说明已经足以支持多数调试。

## 先建立失败分类，再改系统

看到坏结果时，先问“哪一层失败”，不要直接给 Prompt 加一句话。

| 失败类型 | 表现 | 优先检查 |
|---|---|---|
| 目标失败 | 做了相邻但错误的任务 | 目标、不做范围、路由 |
| 上下文失败 | 漏用关键材料或引用旧版 | 选择、版本、压缩、恢复 |
| 工具失败 | 选错工具、参数或结果解析错误 | 工具描述、Schema、异常处理 |
| 证据失败 | 结论无来源或来源不支持 | 取证规则、来源等级、验证 |
| 权限失败 | 越权、漏确认、授权范围外延 | 权限矩阵、审批快照、硬拦截 |
| 状态失败 | 重复、跳步、跨会话丢进度 | 状态结构、写回和恢复 |
| 交接失败 | 下一 Agent 丢了目标或依据 | handoff 字段、输入过滤、产物位置 |
| 终止失败 | 太早结束或无限重试 | 完成条件、预算、熔断、升级规则 |
| 表达失败 | 内容正确但格式或读者不适配 | Template、示例和输出检查 |

失败分类让你修改正确的资产。例如：来源总是错，增加文风规则没有用；应修改检索范围、工具路由和证据检查。

## Agent Eval 的五类样例

一个真实 Eval 集不只放“正常任务”：

1. **标准样例**：输入完整，验证基本闭环。
2. **混乱样例**：资料多、旧版和新版并存，测试上下文选择。
3. **缺失样例**：必要字段为空，测试是否诚实停下。
4. **冲突样例**：两条来源或两位负责人意见冲突，测试升级规则。
5. **权限样例**：任务诱导它发送、覆盖或扩大范围，测试硬边界。

如果系统会面对恶意输入，还应增加提示注入、敏感数据和工具滥用样例。

## 同时评结果和轨迹

以“会议纪要 Agent”为例：

| 维度 | 检查对象 | 通过标准 |
|---|---|---|
| 结论准确 | 输出 | 只记录明确达成的结论 |
| 待办完整 | 输出 | 动作、负责人、时间；缺失则标待确认 |
| 来源忠实 | 过程 | 每条结论可定位到会议记录 |
| 工具范围 | 过程 | 只读会议材料，只写草稿目录 |
| 人工门 | 过程 | 对外分发前等待批准 |
| Handoff | 过程 | 未确认项和产物位置完整传递 |
| 终止纪律 | 过程 | 输入不足时不擅自补全 |

通过线应包含不可被平均分掩盖的硬失败：例如总分很高，但出现一次擅自发送，就不能发布。

```text
平均分 >= 8/10
来源忠实和不确定性 >= 1/2
零次越权动作
零次把未确认意见写成正式结论
所有受阻样例都给出明确下一步
```

阈值是内部默认，应根据实际风险调整，不是行业标准。

## 版本回归：修复不能破坏旧能力

每次修改 Prompt、Skill、Workflow、工具或模型，都可能让旧样例退化。建议把资产版本与 Eval 结果绑定：

```text
能力包 v0.3 + 模型/配置 A
-> 标准集 5/5
-> 冲突集 1/2 失败
-> 修改 handoff 和停止规则
-> 能力包 v0.4
-> 全量重跑旧 7 个样例 + 新失败样例
```

只有修复了新失败，且旧通过项没有明显退化，才发布新版本。

不要只比较平均分，还要比较：

- 哪类失败增加或减少。
- 成本和时延是否超限。
- 人工确认次数是否合理。
- 是否出现新的高风险错误。
- 结果是否可复现。

## 从 Trace 到资产修改

一次“竞品周报漏掉官网更新”的复盘：

1. **看输出**：周报缺失一条重要变化。
2. **看 trace**：Agent 只调用了搜索引擎，没有读取竞品官网清单。
3. **定失败类型**：工具路由失败，不是写作失败。
4. **找规范资产**：修改 Workflow 的必查来源步骤和工具触发说明。
5. **加 Eval**：加入“搜索无结果但官网有更新”的样例。
6. **回归**：新版本跑全部历史样例。
7. **发布**：记录变更原因、通过结果和剩余风险。

这就是失败回流：现实中的坏结果成为下一版本的测试资产。

## 可观测性的隐私边界

Trace 可能包含用户输入、工具参数、文档内容和外部动作。记录前要决定：

| 问题 | 需要的规则 |
|---|---|
| 是否含敏感数据 | 默认脱敏，必要字段最小化 |
| 谁能查看 | 按任务和角色授权 |
| 保存多久 | 根据调试、审计和政策设期限 |
| 能否用于训练/改进 | 明确用户和组织授权 |
| 能否跨客户汇总 | 只回流脱敏的失败类型和指标 |

可调试性不能自动覆盖隐私和保密义务。

## 验收标准

完成这一讲后，你应该能：

- 区分输出质量、过程质量和业务结果。
- 说明 trace 至少要记录哪些可验证事件。
- 用失败分类把问题路由到正确资产。
- 设计覆盖标准、缺失、冲突和权限的样例集。
- 写出包含硬失败的通过线。
- 把一次失败转成新 Eval 和能力包版本变更。
- 为 trace 设置敏感数据边界。
