# Skill、SubAgent 与多 Agent 分工

<!-- PRACTICE:START -->
> **S6 · Skill / AgentOS · 当前作品：能力资产包**

## Skill、SubAgent 和主 Agent 如何取舍？

Skill 让主 Agent 按需获得方法，SubAgent 用独立上下文隔离重任务；前者保留连续性，后者降低噪声但增加 handoff 成本。

### 在固定研究简报中操作

按中间信息是否要回主上下文、隔离要求和交接成本选择 Skill 或 SubAgent，并写最小 handoff。

### 在「Skill、SubAgent 与多 Agent 分工」中最容易犯的错

为了‘多 Agent’而拆分会增加交接损耗；重任务塞进主上下文又会污染后续判断。

### 「能力资产包」应留下什么证据

- **结构检查**：选择依据包含上下文连续性、隔离、噪声与 handoff 成本，交接可独立接续。
- **固定案例对照**：说明这次修改解决了哪一种失败，并保存进「能力资产包」。
- **需人工核验**：事实、业务适用性与高风险决定仍由人负责。

本页为主脊柱增加 **适用边界、handoff、registry、owner、版本与反馈回流**；满足以上证据后，回到作品继续推进 把能力迁移到新任务并用失败样本升级版本。

## 深入理解与原有知识

## 一句话结论

Skill 解决“主 Agent 如何获得一套可复用能力”，SubAgent 解决“如何把一项工作放到独立上下文中执行”，多 Agent 编排解决“多个执行单元如何分工、交接和汇总”。三者可以组合，但每增加一层都会增加上下文、路由、权限和验证成本。

先问任务边界，再选组织方式；不要因为“可以多 Agent”就拆成团队。

## 三个概念不要混用

| 概念 | 核心作用 | 上下文特点 | 典型产物 |
|---|---|---|---|
| Skill | 给当前 Agent 一套场景能力 | 通常在需要时加载进当前工作上下文 | 方法、参考、工具说明、脚本、检查规则 |
| SubAgent | 委托一个独立执行单元处理子任务 | 独立上下文，只接收明确任务和材料 | 结论、产物、状态、证据、风险 |
| 多 Agent 编排 | 组织多个专门单元共同完成目标 | 多个上下文之间需要路由和 handoff | 汇总结果、依赖状态、协作记录 |

一个 Skill 也可以在 SubAgent 中运行；一个主 Agent 可以把多个 Agent 当工具调用；handoff 也可以把对话控制权交给另一个 Agent。不要把目录格式当成概念本身。

## “同一张桌子 / 另一张桌子”判断法

可以用两张工作台理解 Skill 与 SubAgent 的取舍：

- Skill 像把能力说明和工具带到主 Agent 的工作台上。信息连续，主 Agent 看得见中间过程，但工作台可能越来越拥挤。
- SubAgent 像把重任务交给另一张工作台。搜索日志、截图和草稿留在那里，主 Agent 只接收交付；代价是交接设计不好会丢信息。

这是一种工作设计方法，不是目录格式。交接必须明确下一 Agent 可以接收哪些历史和输入；上下文隔离不是“全传或不传”，而是按任务过滤并结构化传递。

## 用五个问题选择

| 判断问题 | 更偏 Skill | 更偏 SubAgent | 更偏多 Agent |
|---|---|---|---|
| 子任务复杂吗 | 低到中等 | 中到高 | 多个中高复杂子任务 |
| 主 Agent 需要全过程吗 | 需要共享中间信息 | 只需要结果和少量证据 | 只需依赖和汇总状态 |
| 中间过程噪声大吗 | 较小 | 很大，适合隔离 | 多条噪声流需分别隔离 |
| 是否要独立权限/工具 | 可与主 Agent 共用 | 需要更小或不同权限 | 各角色权限不同 |
| 子任务能否独立验收 | 与主任务紧耦合 | 有清楚交付合同 | 多个交付可分别验收再合并 |

如果子任务不能独立描述输入、输出和验收，就不适合先拆成 SubAgent。拆分不会自动让问题更清楚，只会把模糊转移到交接处。

## 一个成熟 Skill 不只是一份 Markdown

入门课程把 Skill 定义为“特定任务的能力包”。进阶时，可以检查它是否包含这些层：

```text
触发层：什么时候用、什么时候不用
方法层：步骤、判断和成功标准
知识层：参考资料、术语和案例
工具层：脚本、工具和最小权限
资产层：模板、素材、种子文件
验证层：validator、清单、样例和失败规则
交接层：产物位置、状态和版本说明
```

成熟 Skill 的最低要求不只是描述“帮我完成任务”，还要覆盖适用/不适用边界、分步工作流、必要参考、资产、执行工具、验证器和交接说明。内部标准把 Skill 视为“知识 + 流程 + 工具 + 资产 + 验证”的组合，而不是一条超长 Prompt。

这不代表每个 Skill 都要有相同目录。最小 Skill 也可以只有：触发、输入、步骤、输出、失败处理和验收。随着真实失败出现，再增加脚本和验证器。

## Skill 应该渐进加载

当 Skill 数量增加，如果把所有正文都放进系统提示词，发现能力本身就会消耗大量上下文。更合理的做法是：

1. 首先只列名称、用途和触发条件。
2. 任务匹配后加载完整 Skill。
3. 需要细节时再读取参考资料和脚本说明。
4. 大产物落文件，只返回摘要和路径。

Skill 加载遵循固定原则：**发现信息要短，执行信息按需，详细参考可取回。**

## SubAgent 的关键不是角色名，而是交付合同

“你是研究员”不能构成有效委托。一个 SubAgent handoff 至少包含：

```text
任务：你要独立完成什么
不做：哪些相邻问题不要扩展
输入：材料和文件位置
工具：允许使用什么
输出：交付格式和产物位置
证据：哪些结论必须带来源
验收：什么算完成
预算：轮次、时间或范围
升级：什么情况必须停止并返回
```

返回时不要只说“完成了”：

```text
状态：completed / blocked / needs-decision
结论：不超过 5 条
证据：来源或文件位置
产物：路径和版本
未完成：明确缺口
风险：可能影响主任务的事项
需要主 Agent 决定：唯一问题
```

## 两种常见编排

### 管理者模式

主 Agent 保留控制权，把 SubAgent 当专用工具：

```text
主 Agent
├─ 调研 Agent
├─ 数据 Agent
└─ 校验 Agent
```

适合主 Agent 必须统一语气、整合证据和做最终决策的任务。风险是主 Agent 容易成为上下文瓶颈。

### Handoff 模式

一个 Agent 把控制权和必要上下文交给另一个 Agent：

```text
入口 Agent -> 售前 Agent -> 交付 Agent
```

适合角色边界清楚、后续角色需要直接与用户继续工作的场景。风险是交接历史太多会污染下一角色，太少又会丢失承诺。

多 Agent 系统可以组合两种模式，但一开始应选择最简单的拓扑。

## 多 Agent 的真实成本

增加 Agent 会带来：

- 路由错误：任务交给了错误角色。
- 上下文重复：多个 Agent 读取同一批长资料。
- 交接损失：来源、假设或用户承诺被压缩掉。
- 冲突：多个 Agent 同时修改同一产物。
- 权限扩散：每个角色都拿到过多工具。
- 验证困难：最终失败不知道由谁引起。
- 成本和延迟：更多模型轮次和工具调用。

只有并行、隔离、专门权限或独立验收带来的收益超过这些成本，拆分才有价值。

## 案例：一份客户方案如何分工

任务包含客户材料整理、竞品核查、方案结构和风险复核。

### 过度拆分

四个 Agent 各自生成一份完整报告，主 Agent 再拼接。结果是重复背景、术语不一、证据冲突。

### 更小的分工

| 单元 | 任务 | 输出 |
|---|---|---|
| 主 Agent + 方案 Skill | 维护目标、结构、客户语境和最终稿 | 方案主文档 |
| 调研 SubAgent | 只核查竞品事实，不写方案建议 | 事实表 + 来源 + 未确认项 |
| 风险 SubAgent | 只检查承诺、合规和缺失依据 | 风险清单 + 阻塞项 |

两个 SubAgent 都把细节放在文件中，返回短摘要。主 Agent 只加载与当前章节相关的证据，最后统一表达。

- 返回结果是否能独立验收？
- 文件路径和版本是否清楚？
- 卡住时只返回一个明确决策问题吗？

## 验收标准

完成这一讲后，你应该能：

- 区分 Skill、SubAgent 和多 Agent 编排的职责。
- 用五问矩阵选择内化能力还是隔离执行。
- 说明一个成熟 Skill 为什么可能包含参考、资产、脚本和 validator。
- 写出输入和返回两侧的 handoff 合同。
- 识别多 Agent 的路由、上下文、权限和验证成本。
- 为任务选择最简单且可验收的协作拓扑。
