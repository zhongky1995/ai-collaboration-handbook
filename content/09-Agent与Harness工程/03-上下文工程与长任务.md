## 长任务怎样在有限上下文中继续和恢复？

长任务的关键不是无限扩大窗口，而是选择、分层、压缩、持久化与恢复；文件和 handoff 是跨上下文传递状态的手段。

### 在固定研究简报中操作

写一份恢复快照：已完成、当前状态、证据位置、未决风险、下一动作与停止原因。

### 在「上下文工程与长任务」中最容易犯的错

把完整历史不断重放会增加噪声；只做摘要又可能丢失证据位置和未决风险。

### 「模板与上下文材料包」应留下什么证据

- **结构检查**：恢复快照能让另一会话从已完成、当前状态、证据与下一动作继续。
- **固定案例对照**：说明这次修改解决了哪一种失败，并保存进「模板与上下文材料包」。
- **需人工核验**：事实、业务适用性与高风险决定仍由人负责。

本页为主脊柱增加 **变量、材料选择、上下文预算、来源与版本**；满足以上证据后，回到作品继续推进 Workflow：把稳定路径写成状态。

## 深入理解与原有知识

## 一句话结论

上下文工程不是“尽量把更多资料塞给模型”，而是每一轮都为当前任务选择最小但足够的高信号工作集，并让重要状态在压缩、换人、换 Agent 和跨会话之后仍能恢复。

Prompt 工程主要关心“指令怎么写”；上下文工程还要管理系统规则、工具说明、外部资料、消息历史、状态、工具结果和记忆何时进入、保留、压缩或退出。

## 上下文是一张工作台，不是仓库

基础课程已经把上下文比作一张工作台。Agent 场景需要再加一层：这张工作台每一轮都在变化。

```text
可用信息全集
  ├─ 稳定规则
  ├─ 当前任务状态
  ├─ 外部资料与文件
  ├─ 工具结果
  ├─ 对话历史
  └─ 长期记忆
        ↓ 选择、排序、压缩
本轮上下文
        ↓ 模型生成动作
新结果与新状态
        ↓ 再选择
下一轮上下文
```

内部标准把上下文工程定义为：持续管理有限的 Token 预算，在每次推理前选择最可能支持当前目标的信息，而不是只在任务开始时写一次 Prompt。

## 每一轮问四个问题

1. **现在要做什么？** 当前阶段和可验收输出是什么？
2. **必须知道什么？** 哪些规则、事实、文件片段和工具说明会改变这一步？
3. **可以忘记什么？** 哪些旧讨论、已解决分支和冗长工具原文已经不再需要？
4. **如何恢复？** 被压缩或移出的细节在哪里，下一位执行者怎样取回？

这四问比“上下文窗口还有多少”更重要。窗口很大，也可能被低价值信息占满；窗口较小，只要工作集清楚，仍能完成复杂任务。

## 给不同信息设预算

上下文失控往往不是某一条信息太长，而是多个“看起来都合理”的内容叠加：系统规则、十几个工具说明、五份文件、搜索结果、截图和聊天历史同时进入。

可以先用比例而不是精确 Token 做预算：

| 内容 | 预算问题 | 建议策略 |
|---|---|---|
| 稳定指令 | 哪些规则每轮都必须出现？ | 保持短、清楚、少变；细节按需加载 |
| 任务状态 | 下一步需要哪些状态字段？ | 用结构化摘要，不复制全对话 |
| 文件资料 | 当前决策真正依赖哪些片段？ | 先目录/摘要，再按位置读取 |
| 工具说明 | 这一轮可能用到哪些工具？ | 只暴露相关工具和最小描述 |
| 工具结果 | 完整结果是否必须直接看见？ | 大结果落文件，带摘要、范围和路径 |
| 历史 | 哪些决定仍然有效？ | 保留决定和原因，移出过程噪声 |
| 输出空间 | 模型还需要多少空间完成工作？ | 不让输入占满全部窗口 |

上下文预算采用统一原则：**总量有上限，单项也有上限；先做局部、低损压缩，最后才整体摘要。** 工具结果、技能列表、文件资料和历史记录都必须分别设置预算，不能只控制总长度。

## 渐进披露：先告诉模型“有什么”

不是所有能力和资料都要一开始完整加载。可以分三层：

```text
发现层：名称、用途、何时使用
选择层：当前任务相关的目录、摘要、字段
执行层：真正需要的完整说明、文件片段、脚本或工具结果
```

例如一个视觉 Skill 可以先只暴露“适合做社交卡片；不适合长视频剪辑”。只有任务匹配时，才加载完整工作流、版式参考和渲染说明。

渐进披露同时改善两件事：减少无关 Token，也降低不同规则互相冲突的机会。

## 压缩不是把一切写短

好的压缩要区分三类信息：

| 处理 | 适合内容 | 例子 |
|---|---|---|
| 保留原文 | 精确内容会影响后续动作 | 已批准文案、合同条款、文件路径 |
| 结构化摘要 | 过程很长，但决定需要保留 | 已尝试方案、结论、失败原因、下一步 |
| 移出并可取回 | 当前不需要，但以后可能查 | 完整网页、长日志、旧版本草稿 |

长任务中常见的“压缩后失忆”，不是摘要不够长，而是没有先定义必须保留的状态。一个续跑摘要至少应该包括：

```text
目标和不做范围
当前阶段
已完成及证据
有效决定及原因
未解决问题
关键文件位置
权限与风险
下一步
```

## 外部文件是上下文的中转站

主 Agent 和 SubAgent 不应在消息里搬运全部资料。详细过程落在可取回的文件中，消息只交换任务状态、结论、证据位置和风险。

```text
主 Agent：任务、边界、材料位置
        ↓
SubAgent：独立读取和工作
        ↓
交付：状态摘要 + 结论 + 证据位置 + 风险
```

这样做不是为了让 AI 少看，而是把“必须同时放在工作台上的内容”和“随时可以去档案柜取的内容”分开。

文件作为中转站时要满足：

- 名称和版本明确。
- 说明内容是否完整或被截断。
- 写明来源和生成时间。
- 交接者能访问。
- 旧版本不会被误当成当前版。

## 长任务的三层连续性

一个跨小时、跨会话或跨 Agent 的任务，需要同时保存：

### 1. 任务连续性

目标、范围、完成条件没有漂移。

### 2. 证据连续性

关键结论仍能找到来源，不能只保留“之前确认过”。

### 3. 操作连续性

接手者知道已经做过什么、哪些动作不能重复、下一步需要什么权限。

只有“总结一下前面的对话”通常只能保留任务连续性，证据和操作仍可能丢失。

## 案例：跨两天完成活动复盘

第一天，AI 读取活动数据、访谈和社媒反馈。不要把全部内容留在聊天里，而是产出：

```text
state.md       当前阶段、已完成、待办、权限
evidence.csv   事实、来源、时间、可信度、冲突
decisions.md   已做判断及原因
draft.md       当前复盘草稿
```

第二天继续时，只把任务、`state.md`、相关证据片段和 `draft.md` 的当前章节放进上下文。需要核查某条反馈时，再按 `evidence.csv` 的来源位置读取原文。

这比把昨天全部聊天粘贴回来更稳定，因为当前工作集和可恢复细节被分开管理。

## 四个反模式

### 反模式一：全量继承

每个 SubAgent 都继承主对话、所有工具、全部规则和历史。结果是隔离名义存在，成本和噪声并未减少。

### 反模式二：静默截断

工具结果被截断，却没有告诉模型范围和完整结果位置。模型会把预览当全集，产生错误判断。

### 反模式三：摘要只写结论

只保留“建议选择方案 A”，没有依据、废弃方案和剩余风险。接手者无法判断这个结论是否仍有效。

### 反模式四：把记忆当事实库

长期记忆适合偏好和稳定背景，不适合保存会变化的价格、项目状态和未核验结论。动态事实应回到当前来源和状态。

## 练习：做一份上下文预算与交接包

选一个需要至少三轮推进的任务：

| 信息 | 本轮必须带 | 按需读取 | 可移出 | 恢复位置 |
|---|---|---|---|---|
| 稳定规则 |  |  |  |  |
| 当前状态 |  |  |  |  |
| 原始资料 |  |  |  |  |
| 工具结果 |  |  |  |  |
| 已做决定 |  |  |  |  |
| 旧讨论 |  |  |  |  |

再写一个不超过 200 字的交接摘要，并附上详细资料位置。让另一个人只看交接包回答：目标是什么、做到哪、依据在哪、下一步是什么、什么不能自动做。

## 验收标准

完成这一讲后，你应该能：

- 区分上下文容量问题和信息密度问题。
- 用四问为一轮任务选择工作集。
- 为指令、状态、资料、工具和输出分别设预算。
- 设计“保留、摘要、移出可取回”的压缩方案。
- 写出同时保留任务、证据和操作连续性的 handoff。
