# 从真实工作到 AgentOS 能力资产

<!-- PRACTICE:START -->
> **S6 · Skill / AgentOS · 当前作品：能力资产包**

## 个人方法怎样成为可治理的能力资产？

能力资产化的闭环是：真实工作→工作卡→能力组合→运行与交接→Eval→失败回流→新版本。本手册把承载这套闭环的组织能力运行体系定义为 AgentOS。

### 在固定研究简报中操作

从一个真实岗位任务生成 registry 条目，区分个人私有经验与可共享方法；个人经验进入共享层前必须脱敏、抽象并通过验收。

### 在「从真实工作到 AgentOS 能力资产」中最容易犯的错

只上传模板而没有 owner、状态、版本和反馈入口，资产会快速失真；私有经验直接共享还可能越界。

### 「能力资产包」应留下什么证据

- **结构检查**：registry 完整、私有/共享边界清楚，一次失败能回流到新版本。
- **固定案例对照**：说明这次修改解决了哪一种失败，并保存进「能力资产包」。
- **需人工核验**：事实、业务适用性与高风险决定仍由人负责。

本页为主脊柱增加 **适用边界、handoff、registry、owner、版本与反馈回流**；满足以上证据后，回到作品继续推进 把能力迁移到新任务并用失败样本升级版本。

## 深入理解与原有知识

## 一句话结论

真正可积累的不是“我有多少条 Prompt”，而是：一项真实工作能否被整理成 AI 可读取、可执行、可交接、可评测、可迭代的能力资产。

在本手册中，AgentOS 不是某个软件或工具清单，而是让个人经验和组织工作方法能够被 AI 读取、执行、交接、评测和迭代的能力运行体系。它要解决的核心问题是：**怎样让有效方法不再困在聊天记录里？**

## 不要从工具清单开始

很多 AI 系统从“我们接了哪些模型、MCP、浏览器和自动化工具”开始设计。结果是能力看起来很多，却不知道服务哪项工作。

更稳的顺序是：

```text
真实工作
-> 谁在什么场景下做
-> 输入、判断、动作、工具、交接、风险和验收
-> 哪些交给 AI，哪些保留给人
-> 再选择 Prompt、Skill、Workflow、Agent 和工具
```

例如“做市场周报”并不是一个足够清楚的场景。继续拆才会发现真实工作可能包括：

- 运营收集本周渠道数据。
- 市场同事解释活动和异常。
- 产品负责人确认版本变化。
- 负责人判断哪些结论能向管理层汇报。
- 最终材料要保留来源、口径和待确认项。

如果直接安装“周报 Agent”，这些组织语义不会自动出现。系统必须先知道谁负责什么、什么算完成、哪些判断不能外包。

## 从工作到能力资产的五步

内部能力资产化标准固定为五步：

```text
1. 工作卡：把真实工作说清
2. 能力映射：决定 AI 需要什么
3. 运行组合：把资产装进 Harness
4. 交接与验收：让过程可接续、结果可负责
5. 失败回流：把真实失败变成下一版本
```

### 第一步：工作卡

一张工作卡至少回答：

| 字段 | 问题 |
|---|---|
| 触发 | 什么时候开始，谁提出？ |
| 目标 | 产出什么结果，服务谁？ |
| 输入 | 数据、文件、系统和背景在哪里？ |
| 判断 | 哪些地方依赖经验或取舍？ |
| 动作 | 要读取、生成、修改、通知还是发布？ |
| 交接 | 上一步给谁，下一步由谁接？ |
| 风险 | 哪些错误会产生客户、财务、合规或声誉成本？ |
| 验收 | 什么证据能说明工作完成？ |

工作卡先描述工作，不急着写“用哪个模型”。这样即使工具更换，核心方法仍可保留。

### 第二步：能力映射

同一项工作通常需要多种资产。不是所有东西都应该写进一个 Skill。

| 资产 | 负责什么 | 市场周报例子 |
|---|---|---|
| Prompt / instructions | 单次判断和表达规则 | 区分事实、解释和建议 |
| Template | 固定输入输出结构 | 渠道数据表、周报结构 |
| Workflow | 稳定步骤和人工门 | 汇总 → 查异常 → 解释 → 审核 |
| Skill | 封装特定场景的方法、参考资料和工具用法 | “市场周报”能力包 |
| Agent / SubAgent | 在不确定路径中观察、选择和执行 | 针对异常渠道继续补查 |
| Tool / connector | 连接真实数据和动作 | 表格、网页、内部系统 |
| State / memory | 记录当前进度和跨期基线 | 上周快照、未确认口径 |
| Handoff | 把必要上下文交给下一角色 | 数据异常交给渠道负责人确认 |
| Guardrail | 阻止越权或高风险动作 | 未审核不得发布给管理层 |
| Eval / trace | 判断稳定性并定位失败 | 口径一致率、来源覆盖、运行轨迹 |

这张表的价值在于分配责任。输出格式漂移可能应该改 Template；步骤顺序错误应该改 Workflow；总是选错数据源可能要改工具说明或路由；越权发布必须由 Guardrail 拦截，而不是只加一句提醒。

### 第三步：运行组合

能力资产只有进入真实任务才产生价值。一个最小运行组合通常包括：

```text
工作卡 + 当前上下文 + 选中的能力资产
-> Harness 运行
-> 产物 + 状态 + 来源 + 风险
```

这里需要一个轻量 registry（资产登记表），让 AI 和人知道“有什么、何时用、当前是哪一版”。

```text
资产名称：市场周报能力包
版本：0.3
适用：有固定渠道数据和负责人复核的内部周报
不适用：财务披露、对外新闻稿
入口：工作卡模板
依赖：渠道数据表、品牌口径、异常核查 Skill
权限：读数据、写草稿；不可外发
Eval：5 个历史周报样例 + 2 个异常样例
负责人：市场运营
最近更新：根据“渠道口径混用”失败案例修订
```

Registry 不需要一开始就做成平台。一个结构清楚的表格或 YAML 文件已经可以让资产被发现、选择和版本化。

### 第四步：交接与验收

当任务跨人或跨 Agent 时，交接不能只写“已完成，请看附件”。至少传递：

| 交接内容 | 作用 |
|---|---|
| 当前目标与状态 | 接手者知道任务进行到哪里 |
| 已完成与未完成 | 防止重复和漏项 |
| 关键依据与来源 | 结论可以回溯 |
| 已做决定及原因 | 避免新 Agent 重开已经关闭的问题 |
| 风险与待确认 | 知道哪里不能自动继续 |
| 产物位置 | 细节放在文件，不挤爆交接消息 |
| 下一步与负责人 | 明确谁在什么条件下行动 |

AI-to-AI 消息必须携带工作语义，并由接收方判断是否需要升级给人。内部通知标准是：**不把所有过程发给所有人，只把需要判断、授权或承担责任的内容送到正确的人。**

### 第五步：失败回流

能力资产的版本不应该只根据作者灵感更新，而要根据真实运行失败更新：

```text
运行失败
-> 记录失败类型和上下文
-> 判断应修改哪类资产
-> 增加或修改 Eval 样例
-> 发布新版本
-> 用旧失败样例回归
```

例如周报把“环比下降 12%”误写成“下降 12 个百分点”。这不是简单的文案问题：

1. 失败记录标为“指标口径混淆”。
2. 在数据模板中分开百分比和百分点。
3. 在 Skill 参考中增加口径说明。
4. 在 Eval 中加入一个相似异常样例。
5. 新版本必须通过旧样例后才能替换当前版。

这样，错误不只是被修掉一次，而是变成系统下一次不再犯错的资产。

## 个人层和组织层要分开

不是所有经验都应该进入共享库。

| 个人私有层 | 组织共享层 |
|---|---|
| 写作偏好、个人习惯 | 组织 SOP、角色边界 |
| 未脱敏客户原始材料 | 脱敏后的场景模式 |
| 私人关系和判断笔记 | 可复用模板、检查清单 |
| 当前工作草稿 | 已验收的能力包版本 |
| 个人 AI 的长期记忆 | 失败类型、Eval 和发布记录 |

个人经验进入组织共享前，应经过：脱敏、抽象、标注适用范围、补验收标准、加入 Eval、明确授权。共享的不是原始隐私，而是可复用的方法。

## 四个反模式

### 反模式一：把文件夹命名为 AgentOS，就认为系统成立

目录只是载体。没有触发、权限、版本、交接和 Eval，它仍然是文档仓库。

### 反模式二：把所有工作都封装成一个万能 Skill

能力越大，触发越模糊、上下文越重、失败越难定位。应按真实工作边界拆分，并让 Workflow 或 Harness 组合它们。

### 反模式三：只沉淀成功案例

成功结果说明“曾经做成”，失败样例才能告诉你系统边界在哪里。没有失败回流，资产只能积累数量，不能积累可靠性。

### 反模式四：组织共享等于全量同步

把每次过程、原始材料和所有通知发给所有人，会制造新的信息负担。共享应围绕职责、风险和下一步路由。

## 练习：做一张能力资产卡

选择一项你每周都会做的真实工作，完成：

```text
工作名称：
触发与目标：
输入：
关键判断：
最终产物：

需要的 Prompt / Template：
需要的 Workflow：
是否需要 Agent / SubAgent，为什么：
需要的工具和权限：
状态与记忆：
Handoff 给谁、传什么：
Guardrail：
Eval 样例：

个人私有内容：
可进入组织共享的抽象：
第一个已知失败：
下一版本修改：
```

不要追求一次填满。先让一项工作从触发到验收闭环，再增加能力。

## 验收标准

完成这一讲后，你应该能：

- 解释为什么能力系统要从真实工作而不是工具清单出发。
- 把一项工作拆成输入、判断、动作、交接、风险和验收。
- 区分 Prompt、Skill、Workflow、Agent、Handoff、Eval 等资产的职责。
- 写出一个轻量 registry 条目和能力资产卡。
- 说明个人经验进入组织共享前需要哪些处理。
- 把一个真实失败转成资产修改和回归样例。
